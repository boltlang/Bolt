Type checking

The type checker lives in the boltlang-hir-ty crate. It works on the lowered bodies and signatures of boltlang-hir-def, so it never looks at syntax: names are already resolved to definitions, parentheses are gone and every expression has an ExprId in an arena.

The algorithm belongs to the Hindley–Milner family [Hindley 1969, Milner 1978, Damas & Milner 1982], extended with qualified types for classes [Jones 1994] and with structural field constraints in the spirit of Ohori's record calculus [Ohori 1995]. In short:

  • Constraints are generated by walking a body once. Every expression gets a type, often a fresh inference variable, and the walk emits three kinds of constraints: two types are equal, some types have an instance of a class, or a type has a field.
  • Equalities are solved right away by a unifier, as in Algorithm W. Class and field constraints are deferred until the types involved are known well enough, which makes the checker an instance of the HM(X) framework [Odersky et al. 1999], with deferral in the style of OutsideIn(X) [Vytiniotis et al. 2011].
  • Expected types flow inwards as hints, so that lambdas, tuples, arrays and branches can use the type their context expects. This is a light form of bidirectional type checking [Pierce & Turner 2000, Dunfield & Krishnaswami 2021].
  • Functions without complete signatures are generalized in groups of functions that call each other, found with Tarjan's algorithm [Tarjan 1972]. Local lets are never generalized [Vytiniotis et al. 2010].
  • Functions with complete signatures are checked on their own, so that editing their bodies never makes their callers be checked again.

The type checker runs inside Salsa, like the rest of the compiler. Every step is a query, so the language server only redoes what an edit affects.

A first example​

class Show[T] { fn show(x: T) -> str; }
impl Show[i32] { fn show(x) = "int"; }
fn twice(x) = (show(x), show(x));
twice(1);
twice(true);

The checker finds:

twice: forall a. Show[a] => fn(a) -> (str, str)
error at `twice`: no instance Show[bool]

Here is what happens:

  1. twice has no signature, so it's inferred. Its parameter gets a variable α\alphaα. show has the declared scheme ∀T. Show[T]⇒fn(T)→str\forall T.\ \mathsf{Show}[T] \Rightarrow \mathsf{fn}(T) \to \mathsf{str}∀T. Show[T]⇒fn(T)→str. Each use instantiates TTT with a fresh variable and adds a deferred constraint Show[β]\mathsf{Show}[\beta]Show[β].
  2. Unification makes β=α\beta = \alphaβ=α. Nothing decides α\alphaα, so the constraint Show[α]\mathsf{Show}[\alpha]Show[α] can't be solved inside twice.
  3. When twice is generalized, α\alphaα becomes the bound variable a. The pending constraint mentions only a, so it becomes part of the scheme instead of an error.
  4. The top-level statements are checked as a separate body. twice(true) instantiates the scheme with bool and emits Show[bool]\mathsf{Show}[\mathsf{bool}]Show[bool], for which no impl exists.
