Kinds

A type parameter can stand for a type constructor, not only a type:

class Functor[F] { fn fmap[A, B](f: fn (A) -> B, x: F[A]) -> F[B]; }

impl Functor[Option] { ... }
impl[E] Functor[Either[E]] { ... }

fn double[F](x: F[i32]) -> F[i32] where Functor[F] = fmap(|n| n * 2, x);

F is applied to arguments, as in F[A], and Option is used without any. The design is Jones's constructor classes [Jones 1995], which Haskell 98 adopted. Type variables can stand for constructors, but there are no type-level functions, so unification stays first-order and type inference keeps its principal types.

What kinds are​

A kind is the type of a type (Kind in kind.rs):

κ::=Type∣κ1→κ2\kappa ::= \mathsf{Type} \mid \kappa_1 \to \kappa_2κ::=Type∣κ1​→κ2​

i32 and Option[i32] are of kind Type\mathsf{Type}Type. Option is of kind Type→Type\mathsf{Type} \to \mathsf{Type}Type→Type, Either of kind Type→Type→Type\mathsf{Type} \to \mathsf{Type} \to \mathsf{Type}Type→Type→Type, and the F of Functor of kind Type→Type\mathsf{Type} \to \mathsf{Type}Type→Type. Applying a constructor of kind κ1→κ2\kappa_1 \to \kappa_2κ1​→κ2​ to a type of kind κ1\kappa_1κ1​ gives a type of kind κ2\kappa_2κ2​, so Either[str] is of kind Type→Type\mathsf{Type} \to \mathsf{Type}Type→Type.

Kinds are not to be confused with the VarKind of inference variables, which says whether a variable is for any type or for a number.

Kind inference​

Kinds are never written. They're inferred from how type parameters are used, by the same algorithm as type inference, one level up [Peyton Jones 2003, section 4.6]:

  1. Every type parameter gets a kind variable.
  2. Every use of a type gives an equation:
    • a type that values have, like a field, parameter or return type, is of kind Type\mathsf{Type}Type;
    • an application T[τ1,…,τn]T[\tau_1, \dots, \tau_n]T[τ1​,…,τn​] gives κT=κτ1→⋯→κτn→β\kappa_T = \kappa_{\tau_1} \to \dots \to \kappa_{\tau_n} \to \betaκT​=κτ1​​→⋯→κτn​​→β, where β\betaβ is the kind of the application;
    • the arguments of a class constraint C[τˉ]C[\bar\tau]C[τˉ] have the kinds of CCC's parameters, and so do the targets of bounds like T: Functor.
  3. The equations are solved by unification, with an occurs check.
  4. Kind variables that nothing decided become Type\mathsf{Type}Type.

The last step is Haskell 98's defaulting. It means there's no kind polymorphism: an unused parameter is of kind Type\mathsf{Type}Type.

Groups​

Parameters are inferred together when their uses are in the same definitions. group_kinds infers one group at a time:

  • a class with its methods, consts and associated types: the kind of Functor's F comes from the signature of fmap;
  • an impl with its items;
  • a struct, enum, type alias or top-level function on its own.

A use of another definition, like Option in a field, takes that definition's kinds from its own group. When definitions of different groups refer to each other, like two structs with fields of each other's type, Salsa detects the cycle and their parameters are all of kind Type\mathsf{Type}Type (group_kinds_cycle). Haskell infers kinds per strongly connected group of declarations instead, which would handle that case. Xie, Eisenberg and Oliveira describe the subtleties of kind inference for datatypes in detail [Xie et al. 2020].

Kind inference doesn't report errors. When the uses of a parameter disagree, the first one wins, and lowering reports the others.

Checking kinds when lowering​

TyLoweringContext checks the kind of every type it lowers. A type in a position for values must be of kind Type\mathsf{Type}Type. An argument must have the kind its constructor expects, and the arguments of a class constraint the kinds of the class's parameters. A mismatch is reported in one of two ways:

  • A constructor missing arguments where a type is expected, like the Option of fn f(x: Option), is reported as "expected 1 type argument, found 0", which is easier to understand. The type becomes Option[⊥], so what's known of it is kept.
  • Anything else is a kind mismatch (E0216), like "expected a type of kind Type -> Type, found i32 of kind Type" for impl Functor[i32].

A type alias must be given all its arguments, since lowering expands it by substitution, and a partially applied alias would be a type-level function.

Types​

Two forms of Ty stand for constructors and their applications:

  • Adt(T, args) can have fewer arguments than T has parameters. Adt(Either, [str]) is the constructor Either[str].
  • App(head, args) is a type parameter or inference variable applied to arguments, like F[A] or β[i32]\beta[\mathsf{i32}]β[i32].

Every type has one form. Ty::app builds applications and normalizes them: an Adt applied to more arguments is a longer Adt, and an App applied to more arguments is a longer App. Ty::fold, and so every substitution, rebuilds applications with Ty::app. So replacing F by Option in F[A] gives Option[A] and not an application of Option, which is what lets an impl's methods be checked against the class's signatures without any special case.

Unification​

Type constructors are generative and injective: F[A]=G[B]F[A] = G[B]F[A]=G[B] only when F=GF = GF=G and A=BA = BA=B. That makes unifying applications first-order [Jones 1995]. Arguments are matched from the right, and whichever side has more arguments gives the rest of them to its head:

F[τ1,…,τm]≐T[σ1,…,σn]⇝F≐T[σ1,…,σn−m], τi≐σn−m+iif n≥mF[τ1,…,τm]≐G[σ1,…,σn]⇝F[τ1,…,τm−n]≐G, τm−n+i≐σiif m≥n\begin{array}{lcl} F[\tau_1, \dots, \tau_m] \doteq T[\sigma_1, \dots, \sigma_n] & \leadsto & F \doteq T[\sigma_1, \dots, \sigma_{n-m}],\ \tau_i \doteq \sigma_{n-m+i} \quad \text{if } n \ge m \\ F[\tau_1, \dots, \tau_m] \doteq G[\sigma_1, \dots, \sigma_n] & \leadsto & F[\tau_1, \dots, \tau_{m-n}] \doteq G,\ \tau_{m-n+i} \doteq \sigma_i \quad \text{if } m \ge n \end{array}F[τ1​,…,τm​]≐T[σ1​,…,σn​]F[τ1​,…,τm​]≐G[σ1​,…,σn​]​⇝⇝​F≐T[σ1​,…,σn−m​], τi​≐σn−m+i​if n≥mF[τ1​,…,τm−n​]≐G, τm−n+i​≐σi​if m≥n​

So β[α]≐Either[str,i32]\beta[\alpha] \doteq \mathsf{Either}[\mathsf{str}, \mathsf{i32}]β[α]≐Either[str,i32] gives β:=Either[str]\beta := \mathsf{Either}[\mathsf{str}]β:=Either[str] and α:=i32\alpha := \mathsf{i32}α:=i32. shallow_resolve resolves the head of an application as well, so that β[i32]\beta[\mathsf{i32}]β[i32] with β:=Option\beta := \mathsf{Option}β:=Option is Option[i32]\mathsf{Option}[\mathsf{i32}]Option[i32].

The price of keeping this first-order is that only the last arguments of a constructor can be abstracted over. Either[E] is a constructor, but "Either with its first argument missing" isn't, and needs a struct that swaps the arguments, as in Haskell.

Instances​

Matching an impl against a class constraint (match_ty in solve.rs) splits applications in the same way, with match_app. The impl head Functor[Either[E]] matches the constraint Functor[Either[str]]\mathsf{Functor}[\mathsf{Either}[\mathsf{str}]]Functor[Either[str]] with E:=strE := \mathsf{str}E:=str. A constraint whose argument is an application of an unknown variable, like Show[β[i32]]\mathsf{Show}[\beta[\mathsf{i32}]]Show[β[i32]], is a Maybe for every impl whose arguments could still match, and waits like any other constraint.

Generalization​

Nothing changes: an inference variable at the head of an application is generalized like any other.

fn double(x) = fmap(|n| n * 2, x);
double: forall a. Functor[a] => fn(a[i32]) -> a[i32]

Methods with type parameters​

A class method can have type parameters of its own, like the A and B of fmap. An impl's method that declares as many is checked with its own in their place, so fn fmap[T, R](f: fn (T) -> R, xs: List[T]) -> List[R] in impl Functor[List] fits. A method that declares none, like fn fmap(f, x) = ..., is checked with the class method's parameters, and they're part of its scheme.
