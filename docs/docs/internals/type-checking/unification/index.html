Unification

The Unifier in unify.rs solves equalities τ1≐τ2\tau_1 \doteq \tau_2τ1​≐τ2​ by binding inference variables. It's syntactic, first-order unification [Robinson 1965], and it knows nothing about where types come from. It returns a UnifyError, and the solver turns that into a diagnostic with an origin.

The variable table​

Variables are indices into a table, where each entry is either Unbound(kind) or Bound(ty). A variable can be bound to another variable, so the table is a union-find structure [Tarjan 1975], which is the usual way to implement unification efficiently [Huet 1976]:

  • shallow_resolve follows bound variables until it reaches a type that isn't a bound variable. It's the find operation, without path compression.
  • resolve replaces every bound variable inside a type, recursively. It's used when a type has to be shown or stored, like in an InferenceResult.

The unifier never substitutes into types eagerly. A type stays as it was built, with variables in it, and is resolved when someone looks at it.

Applications of type parameters and variables, like F[A], are unified by their last arguments first; Kinds explains how.

Equalities are unified the moment they're emitted, so the order of constraint generation decides which mismatch is reported when a program has several. See Errors for how errors are attributed.

The occurs check​

Binding α:=τ\alpha := \tauα:=τ when τ\tauτ contains α\alphaα would make an infinite type. In fn f(x) = f([x]);, x has type α\alphaα and the recursive call needs α≐[α]\alpha \doteq [\alpha]α≐[α]. bind resolves τ\tauτ fully and checks that α\alphaα isn't in it. If it is, it returns UnifyError::Occurs, which becomes an "infinite type" error.

Numeric variables​

Each variable has a VarKind, and binding respects it:

KindCan be bound to
GeneralAny type.
IntInteger types, like i32 or u8.
Floatf32 and f64.

Unifying two variables joins their kinds. General joined with Int gives Int, but Int joined with Float is a mismatch. So in fn inc(y) = y + 1;, the variable of y meets the Int variable of 1 and becomes an Int variable, which later defaults: inc has type fn(i32) -> i32.

When a body is done, default_numeric_vars binds the Int and Float variables that are still unbound to i32 and f64, and remembers which variables were defaulted. Error messages use that to show a literal as {integer} rather than i32: in let a: f64 = 1;, nobody wrote an i32.

These kinds are a small case of what the type class literature calls defaulting; Haskell does the same with Num and Fractional [Peyton Jones 2003].

Never and error​

Two types are special:

!≐τ⇝done⊥≐τ⇝done! \doteq \tau \leadsto \text{done} \qquad \bot \doteq \tau \leadsto \text{done}!≐τ⇝done⊥≐τ⇝done

! fits everywhere. A diverging expression has type !, and Bolt has no subtyping or coercions, so the unifier accepts ! against any type. It doesn't bind a variable to !. In if c { return 1 } else { 2 }, the branches have types ! and βInt\beta_{\mathsf{Int}}βInt​, and the if gets the integer type, not !.

The error type fits everywhere, so that an error doesn't cause others. Here too the variable isn't bound, because later constraints may still decide it:

match s { Nope(x) => x, _ => 0.0 }

If Nope doesn't exist, the first arm has type ⊥\bot⊥, but the second arm still makes the match a float. Instead of binding, the unifier records in met_error that the variable met an error. When inference is done, error_unknowns binds the variables that met an error and are still unknown to ⊥\bot⊥. Otherwise a variable that's only unknown because of an error would be generalized: fn h() = 1..2 would get the type forall a. fn() -> a, which is wrong and causes confusing errors at its callers.

Tests​

The unit tests at the bottom of unify.rs cover binding, mismatches, the occurs check, numeric kinds and the special types.
