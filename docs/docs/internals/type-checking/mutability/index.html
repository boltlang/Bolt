Mutability

Not compiled yet

The type checker and the evaluator implement this page (#195). The code generator doesn't compile arrays or structs yet: see #177 and #179. The design was decided in #196.

Arrays and structs are shared: let ys = xs makes ys another name for the same array, and let q = p another name for the same struct, as in JavaScript, Java and OCaml. Passing one to a function passes a pointer, and a function can fill in what it's given.

Sharing breaks what mut on a variable promises:

let mut xs = [1, 2];
let ys = xs;     // not `mut`
xs[0] = 9;
ys[0];           // 9: `ys` changed anyway

This page describes how the type checker keeps a promise that sharing can't break. Whether an array or a struct can be changed is part of its type, and every name for it has the same type, so they all agree.

Arrays and structs have a mutability​

The type of an array or a struct has a mutability, which is Mut or Imm:

[τ]  =  Array[μ,τ]S[τ1,…,τn]μμ::=Mut∣Imm∣α[\tau] \;=\; \mathsf{Array}[\mu, \tau] \qquad S[\tau_1, \ldots, \tau_n]^\mu \qquad \mu ::= \mathsf{Mut} \mid \mathsf{Imm} \mid \alpha[τ]=Array[μ,τ]S[τ1​,…,τn​]μμ::=Mut∣Imm∣α

Mut and Imm are types of their own kind. A mutability can be an inference variable, like any type, and it's unified and generalized like one. That's all the type checker needs: no subtyping, and no new kind of constraint. A struct's mutability isn't one of its type arguments, so it doesn't change its kind: Box is still of kind Type→Type\mathsf{Type} \to \mathsf{Type}Type→Type.

In source code, and when types are shown:

WrittenMeans
mut [i32], mut Pointcan be changed
imm [i32], imm Pointcan never be changed, by anyone
[i32], Pointeither: see annotations

Only arrays and structs have a mutability. An enum can't be changed in place: match gives the values of its fields, and there's no way to assign to one. A tuple is still a value, copied when it's assigned, so t.0 = 1 needs let mut t as before. mut before anything else, like mut i32 or mut Option[i32], is an error (E0222).

Something can be changed only if its type is mut:

fn push[T](xs: mut [T], x: T);    // in `std`

let xs = mut [1, 2];
xs.push(3);      // fine
xs[0] = 9;       // fine

let p = mut Point { x: 0, y: 0 };
p.x = 5;         // fine

let ys = [1, 2];
ys[0] = 9;       // error: `ys` is `imm [i32]`, which can't be changed

Assigning to an element, xs[i] = e, needs xs to be a mut array, and assigning to a field, p.x = e, needs p to be a mut struct. So does calling a function whose parameter is mut, like push. What decides is the innermost array or struct of the place that's assigned to: in l.a.x = 1, it's l.a, and in xs[0].x = 1, it's xs[0].

Where the mutability comes from​

The expression that makes an array or a struct decides whether it can be changed. Variables only pass it on:

  • [1, 2] and Point { x: 0, y: 0 } can't be changed: imm [i32] and imm Point.
  • mut [1, 2], mut [], mut Point { x: 0, y: 0 } and, for a tuple struct, mut Meters(1.0) can be changed.
  • A function's result has the mutability of its type: Vec.new() could return mut [T], and xs.copy() a new mut [T].
  • mut before a variant, like mut Shape.Circle { radius: 1.0 }, or before the call of a function, is an error (E0222).

let mut no longer has anything to do with the contents of an array or a struct. It only means the variable can be assigned again:

let xs = mut [1];
xs.push(2);         // fine: the array is `mut`
xs = mut [3];       // error: `xs` isn't `mut`

let mut ys = [1];
ys = [2, 3];        // fine: the variable is `mut`
ys.push(4);         // error: the array isn't

Aliases share the mutability​

let ys = xs unifies the types of ys and xs, mutability included. So an alias of a mut array or struct is mut too, without saying so:

let xs = mut [1, 2];
let ys = xs;        // `mut [i32]`, like `xs`
ys.push(3);         // fine, and `xs` sees it

Since this is unification, it works however the alias is made: through a function, a branch, a struct or a closure.

fn id(x) = x;

let a = id(xs);                         // `mut [i32]`
let b = if c { xs } else { mut [] };    // `mut [i32]`
let get = || xs;                        // `mut fn() -> mut [i32]`

An alias can't change the mutability. Unifying Mut with Imm is an error:

let xs = mut [1, 2];
let ys: imm [i32] = xs;   // error: expected `imm [i32]`, found `mut [i32]`

S { ..base } copies the fields it doesn't give from base, so it can make a struct of another mutability from it, like a mut Point from an imm one. But the copy is shallow: an array, struct or function in a field is shared with base, which would make it an alias with another mutability. So when a field that's copied holds one with the struct's own mutability, base must have the same mutability as the struct:

let q = mut Point { ..p };   // fine, whatever `p` is: the fields are numbers
let l = mut Line { a: mut Point { x: 1, y: 2 }, b: mut Point { x: 3, y: 4 } };
Line { ..l }                 // error: expected `imm Line`, found `mut Line`
Line { a: Point { x: 0, y: 0 }, b: Point { x: 0, y: 0 }, ..l }   // fine: nothing is copied

imm is deep​

What an imm value holds can't be changed either. Otherwise an imm Line could hold a mut Point, and the line would change after all. Three rules make it so.

A field has the mutability of its struct. An array or struct in a field without mut or imm has the struct's own mutability, which is a hidden parameter of the struct:

struct Point { x: i32, y: i32 }
struct Line { a: Point, b: Point }      // `Line^m` has `a: Point^m`

let l = mut Line { a: mut Point { x: 0, y: 0 }, b: mut Point { x: 1, y: 1 } };
l.a.x = 5;                              // fine

let k = Line { a: Point { x: 0, y: 0 }, b: Point { x: 1, y: 1 } };
k.a.x = 5;                              // error: `k.a` is `imm Point`

Line { a: mut Point { x: 0, y: 0 }, ... }   // error: expected `imm Point`, found `mut Point`

A field can be imm, which stays imm in a mut struct, but it can't be mut (E0224): a mut field in an imm struct would break the rule. To change what a field holds, make the struct mut.

The fields of an enum, which has no mutability, are imm. An enum holds something that can be changed only through a type parameter, like Option[mut Point].

An imm value can't hold a mut one through a type parameter. A generic struct's fields have the types it's given:

struct Box[T] { item: T }

let a = mut Box { item: mut Point { x: 0, y: 0 } };   // fine
let b = Box { item: mut Point { x: 0, y: 0 } };       // error (E0223): an `imm Box[mut Point]` can't hold a `mut Point`
let c = [mut [1]];                                    // error (E0223): an `imm [mut [i32]]` can't hold a `mut [i32]`

What a struct holds is what its fields hold, not its type arguments (#256): with struct Handler[T] { f: fn(T) -> () }, an imm Handler[mut [i32]] is fine, since a closure doesn't hold what it takes, and with struct Frozen[T] { items: imm [T] }, only an imm T can be held, in a Frozen of either mutability. That's the same as Rust inferring T: 'a from a struct's fields, and it's what makes a struct type well-formed (StructDecl.atMost_ty_iff in lean/BoltMut/Structs.lean).

Unification can't express this, since it's about a type and what's inside it. It's an "at most" constraint instead, with imm ⊑ mut (#243): an array or struct holds only what's at most its own mutability. So [x] needs nothing in the type of x to be more mut than imm. What an array or struct holds must in turn be at most its mutability, and a function's mutability covers what it captured; what it takes and gives isn't looked into, so an imm [fn(mut [i32]) -> ()] is fine.

The constraint decides what's unknown when only one choice works: a mutability that must be at most imm is imm, and one that something mut must be below is mut. What's left about a function's parameters becomes part of an inferred function's type, and its callers must meet it, like class constraints:

fn wrap(x) = Box { item: x };     // forall a. a: imm => fn(a) -> imm Box[a]
wrap(1);                          // fine
wrap(mut [1]);                    // error (E0230): expected a type that's at most `imm`, found `mut [i32]`

A signature says it with a bound, T: imm, read as "nothing in T is more mut than imm", like Rust's T: 'a for lifetimes. It can be written next to the parameter or in a where clause, and a mutability can be bounded too, as in 'v: 'm:

fn wrap[T: imm](x: T) -> imm Box[T] = Box { item: x };
fn reader(xs: 'v [i32]) -> 'f fn() -> i32 where 'v: 'f = || xs[0];
impl[T: imm] ToImm[[T]] { ... }          // checked where the impl is chosen
struct Frozen[T: imm] { item: T }        // checked where a value is made

Without the bound, a complete signature is an error where it needs one: in fn hide[T](x: T) -> i32 { let b = Box { item: x }; 0 }, T may be mut. A mut struct can hold anything, so mut Box { item: x } needs nothing. A mutability on its own isn't a type: let x: imm = 1 is an error (E0231). A mut array or struct inside an imm one is still also caught once the types are known (E0223), which shows the whole type.

A closure that can change what it captured is mut. A closure shares the variables it captures with the code around it, so it can hold state:

let mut n = 0;
let next = || { n += 1; n };   // `mut fn() -> i32`

A function type has a mutability like an array's. A closure is mut if it captures a let mut variable, even only to read it, or a value that holds something mut: a mut array, struct or function. Otherwise it's imm, and so is a named function, which captures nothing. An imm value can't hold a mut fn, by the rules above:

struct Holder { poke: fn() }       // `poke` has the struct's mutability
let xs = mut [0];

Holder { poke: || { xs[0] += 1; } }       // error: expected `fn() -> ()`, found `mut fn() -> ()`
mut Holder { poke: || { xs[0] += 1; } }   // fine
[|| { xs[0] += 1; }]                      // error (E0223): an `imm [mut fn() -> ()]` can't hold a `mut fn() -> ()`

Calling a function doesn't need it to be mut, unlike Rust's FnMut: a mut fn can't be reached from an imm value anyway. So a function type written without mut or imm in a signature takes either, like [T], and higher-order functions need no annotations: fn twice(f, x) = f(f(x)) takes a counting closure as well as a named function. mut fn() -> T and imm fn() -> T say which one. An imm fn is shown as just fn, since most are, unless that would make two types in a message look the same.

What a closure captures is at most its mutability, by the same "at most" constraint, and a let mut variable makes it mut. So a generic function that makes a closure says how the closure's mutability depends on what it captured:

fn reader(xs: [i32]) = || xs[0];            // 'm: 'n => fn('m [i32]) -> 'n fn() -> i32
fn always[T](x: T) -> fn() -> T = || x;     // forall T. T: 'm => fn(T) -> 'm fn() -> T
fn compose(f, g) = |x| f(g(x));             // forall a b c. 'm: 'o => 'n: 'o => fn('m fn(a) -> b, 'n fn(c) -> a) -> 'o fn(c) -> b

reader([1]) and always(1) are imm closures, and reader(mut [1]) is a mut one.

In std, an FnIter whose function counts is mut, like the one that for x in xs uses for an array or a Vec.

A mut value can hold imm ones. mut [[i32]] is an array that can be changed, of arrays that can't.

What this guarantees​

An imm value, and everything it holds, never changes. All the names for a value have the same type, so if one of them can't change it, none can, and an imm value only holds imm ones. A mut value can't be seen as imm, which is what makes imm worth having:

  • code can rely on an imm value it's given staying the same;
  • values that can't be changed can be shared freely, and their literals can be constants: a data segment in Wasm, made once;
  • an imm struct can't be told apart from a copy, so the code generator can store small ones by value;
  • the reactive design knows what can change, and which calls change it, from the types (#200).

It doesn't guarantee what Rust does, that nothing else changes a mut value while you have it. mut values are shared on purpose.

Functions​

A function without annotations gets the mutability it needs, and is generalized over the rest, like over any type:

fn size(xs) = array_len(xs);               // fn([a]) -> i32
fn fill(xs: [i32], x) { xs[0] = x; }        // error: `xs` isn't `mut`
fn fill(xs: mut [i32], x) { xs[0] = x; }    // fn(mut [i32], i32) -> ()

size is generalized over the mutability of its argument, ∀μ α. Array[μ,α]→i32\forall \mu\, \alpha.\ \mathsf{Array}[\mu, \alpha] \to \mathsf{i32}∀μα. Array[μ,α]→i32, and that's shown as [a]. It takes arrays of either mutability, which makes its argument read-only in its body, not unchanging: a mut array can still be changed during the call through another name for it, like by a closure that the caller passed too. Only imm promises that nothing changes it. fill needs a mut array, since it changes its argument. Instantiating a scheme gives a fresh mutability, so each call can pass a different kind of array.

Indexing goes through the prelude's classes, so a function that indexes an argument whose type it doesn't know is generic over the class instead: fn first(xs) = xs[0] is forall a. Index[a] => fn(a) -> a.Item, and fn set(xs, x) { xs[0] = x; } is forall a. IndexMut[a] => fn(a, a.Item). The impl IndexMut[mut [T]] only covers mut arrays, so set([1], 2) is an error.

A field of a value whose type isn't known is a field constraint. One that's assigned to says so, and needs a mut struct once the type is known:

fn move_x(p) { p.x = 5; }          // forall a. mut a.x: i32 => fn(a) -> ()

move_x(mut Point { x: 1, y: 2 });  // fine
move_x(Point { x: 1, y: 2 });      // error: a field of an `imm Point` is changed here

Annotations​

[T] and Point in the parameters of a function and in a body mean either mutability: a fresh mutability, like _ stands for a fresh type. mut and imm ask for one.

In a function's signature, a fresh mutability is a hidden parameter of the function, like the generalized μ\muμ of first above:

fn sum(xs: [i32]) -> i32 { ... }   // forall m. fn(Array[m, i32]) -> i32

let xs = mut [];
xs.push(1);
sum(xs);           // fine
sum([1, 2]);       // fine

sum takes both kinds of array. Inside its body, the mutability of xs is a parameter, not Mut, so sum can't change xs: xs.push(1) there is an error. That's the same rule as for any type parameter: a function that takes a T can't assume that T is i32. So a signature promises to leave an array or struct alone unless it says mut, and callers don't have to care which kind they pass.

It doesn't promise that the value stays the same while sum runs: the caller may have a mut name for it. imm is for code that relies on a value never changing, like a cache keyed by it, or the reactive design deciding that something can't change. Few functions need it, which is why it isn't what [T] means.

In a let annotation, [T] is an inference variable, which the value decides:

let a: [i32] = mut [1];     // `mut [i32]`
let b: [i32] = [1];         // `imm [i32]`

Return types​

A hidden parameter is chosen by the caller, so it can't be the mutability of something the function makes: fn make() -> [i32] = [1, 2] would be wrong for a caller that asks for mut. Instead, the body decides the mutabilities that a return type doesn't say:

fn primes() -> [i32] = [2, 3, 5];           // `fn() -> imm [i32]`
fn buffer() -> [u8] = mut [0; 1024];         // `fn() -> mut [u8]`
fn next(n: Node) -> Node = n.next;           // the mutability of `n`
fn fixed() -> imm [i32] = mut [];            // error: expected `imm [a]`, found `mut [a]`

next returns what it's given, so its result has its argument's mutability: next(a) is a mut Node for a mut Node a, and an imm Node for an imm one.

That makes the signature incomplete: such a function is inferred, not checked on its own, so editing its body checks its callers again. Writing mut, imm or a name in the return type makes it complete: fn next(n: 'm Node) -> 'm Node says what the body of next would decide, and is checked on its own. A function without a body, like a class method, has no body to decide, so its return type is imm where it doesn't say.

The type of a const and an array or struct in a where predicate, like the [T] of where Show[[T]], are imm too.

An impl gets hidden parameters like a function: impl Size[Point] is for points of either mutability, and impl Size[mut Point] only for those that can be changed.

Type aliases​

A type alias doesn't decide what [T] or Point means in it: the type it's used in does. With type Ints = [i32], fn sum(xs: Ints) takes either kind of array, and mut Ints is mut [i32].

Naming a mutability​

A name like 'm, written where mut or imm would be, is a mutability that's the same wherever the name is:

fn next(n: 'm Node) -> 'm Node = n.next;
fn both(a: 'm [i32], b: 'm [i32]) -> i32 = a[0] + b[0];
fn pair(a: 'm [i32], b: 'n [i32]) -> ('m [i32], 'n [i32]) = (a, b);

next gives back a node with the mutability of the one it's given, both takes two arrays of the same kind, and pair two arrays of any kinds, which it gives back as they are. ' marks the name, as for labels and Rust's lifetimes: without it, m [i32] would be the type m applied to i32.

  • A name is a parameter of the function or impl whose signature it's in, like a hidden one, but shared: every 'm in the signature, its where predicates and its body is the same. Names don't need declaring: using one is enough. Like a hidden parameter, the caller chooses it, so the function can't change what has it, and fn make() -> 'm [i32] = [1] is an error: [1] is imm, not whatever the caller chooses.

  • Only functions, impls and structs have names. An impl's associated types can use its names too: impl[T] Iterable['m FnIter[T]] { type Iter = 'm FnIter[T]; ... } is for an FnIter of either mutability, and its Iter has the same one. An impl's names, like its type parameters, must be in its instance, since that's all choosing the impl decides: impl[T, 'v] Iterable[Vec[T]] is an error (E0234), and impl[T] Iterable['v Vec[T]] is what's meant. A struct declares its names, for its fields: see below. A name elsewhere, like in a const, a type alias outside an impl, a body that isn't its function's or a field whose struct doesn't declare it, is an error (E0225). A name before a type that can't have a mutability, like 'm i32, is E0222.

  • Types show names, and a name for a mutability that's shared but not written: one that a body decides, or a variable of an inferred function. Such names start at 'm, so that they don't read like the type variables a, b, ...:

    fn pick(c, a, b) = if c { array_len(a); a } else { b };  // forall a. fn(Bool, 'm [a], 'm [a]) -> 'm [a]
    fn same(xs: [i32]) -> [i32] = xs;                         // fn('m [i32]) -> 'm [i32]
    fn size(xs) = array_len(xs);                              // forall a. fn([a]) -> i32

    A mutability that appears once isn't named: it's either, and it isn't linked to anything.

Names in structs​

A field without mut or imm has its struct's mutability, so a mut iterator can't hold an imm array. A struct can declare a name for a field instead, after its type parameters (#243):

struct VecIter[T, 'v] { data: 'v Vec[T], index: i32 }

fn start[T](v: 'v Vec[T]) -> mut VecIter[T, 'v] = mut VecIter { data: v, index: 0 };

start takes a Vec of either mutability, and gives a mut iterator over it: the iterator's index can change, and its data has the mutability of v. A type gives the names after its type arguments, like VecIter[i32, imm]. One that isn't given is decided like the mutability before a type: a parameter in a function's signature, an unknown in a body, and the struct's own in a field. More than the struct declares is an error (E0232), and so is a name declared by an item that isn't a struct, a function or an impl (E0233). A function or an impl can declare its names too, but doesn't have to.

A name is at most its struct's mutability. An imm VecIter[i32, mut] would hold a mut Vec, which imm being deep rules out. So making a struct adds 'v ⊑ m for each name its fields have, where m is its mutability, and what a field with a name holds is at most that name: T ⊑ 'v for data: 'v Vec[T]:

mut VecIter { data: mut_vec, index: 0 }   // fine: mut VecIter[i32, mut]
VecIter { data: mut_vec, index: 0 }       // error (E0223): an `imm VecIter[i32, mut]` can't have a `mut` mutability argument
fn frozen[T](v: 'v Vec[T]) -> imm VecIter[T, 'v] where 'v: imm = VecIter { data: v, index: 0 };

The last one needs 'v: imm, or 'v could be mut. It doesn't need T: imm: v is a 'v Vec[T], so T ⊑ 'v, which it can assume, since v exists. A struct can bound its names, like its type parameters, which is checked where a value is made: struct Frozen['v: imm] { data: 'v [i32] }.

A struct update, VecIter { index: 1, ..it }, keeps the names of it, since the fields it doesn't give are shared. Types show a name that's known, like VecIter[i32, imm], and leave one out that's generic and appears once, like the mutability before a type: VecIter[T]. One that's left out before one that's shown is '_.

Making a value that can't be changed from one that can​

A mut value can't become imm, since a mut name for it may still exist. Turning one into the other copies it:

fn freeze[T](xs: [T]) -> imm [T];    // a copy that can't be changed
fn thaw[T](xs: [T]) -> mut [T];      // a copy that can

Since imm is deep, freezing copies everything a value holds that's mut. Freezing without a copy needs to know that no other name refers to the value: that it's unique. Jane Street's OCaml has a mode for that [Lorenzen et al. 2024], and it could come later.

Passing or assigning a value of the wrong mutability is an ordinary type mismatch, which shows both:

[E0201] Error: expected `mut Point`, found `imm Point`

These can show up far from their cause: the push fails because of where the array was made, maybe much earlier. The error should point at where the Imm came from: the literal, the annotation, or the function whose result it is. That's what the labels for the causes of constraints in #127 are for, and why unification will have to remember the origin of Imm and Mut.

Implementation​

  • Types (ty.rs): Ty::Array holds the mutability and the element type, and Ty::Adt holds a struct's mutability after its arguments. An enum's is always Imm, and isn't shown. A mutability is Ty::Mutability(Mut | Imm), an inference variable of kind VarKind::Mutability, a type parameter, or the error type.

  • Lowering (lower.rs): mut [T], imm [T], mut Point and imm Point lower to their mutability, and the rest to Ty::Unwritten, which each item then replaces with Ty::fill_unwritten:

    • in a function's parameters and an impl's instance, hidden parameters, numbered after the declared type parameters (FnSig::hidden, ImplHeader::hidden), so that instantiating a scheme and matching an impl handle them like any other parameter;
    • in a body, and in the return type of a function with a body, inference variables, which the body decides (infer.rs, check.rs);
    • in a struct's field, the struct's own hidden parameter (struct_mutability), which a struct's type substitutes with its mutability (struct_args);
    • in an enum's field, the return type of a function without a body, a const and a where predicate, Imm;
    • in a type alias, nothing: the type it's used in decides.

    A name like 'm lowers to a parameter of its function or impl (named_mutabilities), numbered after the declared type parameters and before the hidden ones. A body can use its function's names. A signature whose return type only has written or named mutabilities is complete.

    A struct's names, like the 'v of struct VecIter[T, 'v] (GenericParams::mutability_params), are parameters after its type parameters and before its own mutability. Ty::Adt holds the arguments for them apart from its type arguments, so that they don't change its kind, and struct_args gives them to its field types. In a type like VecIter[i32, imm], a mutability on its own is one of them; those not given are Ty::Unwritten.

  • Unification (unify.rs): mutabilities are equal or they aren't; there's no subtyping. Ty::Fn holds its mutability last, and fn(...) lowers with Ty::Unwritten like an array, so it's a hidden parameter in a signature and the struct's own in a field.

  • Inference (infer.rs): an array or struct literal is Imm, or Mut with mut. Indexing, field access, for and patterns take either.

    • check_place looks for the innermost index, or field of a struct, in the place that's assigned to. Its array or struct must be mut, and a mutability that isn't known yet becomes Mut (Solver::require_mut). A field of a value whose type isn't known yet marks its field constraint as assigned (FieldConstraint::assign), and solving it requires Mut. Without an index or a field of a struct, the variable must be mut, as before.
    • Making an array or struct adds an AtMostConstraint: the element type is at most the array's mutability, and what a struct's fields hold at most theirs, once its fields are checked. What a struct's fields hold is holds::struct_atoms: the atoms of "the fields are at most the struct's own mutability", like 'v ⊑ m and T ⊑ 'v, with a field that's a struct using that one's, as a fixed point for structs that refer to each other. A body assumes what makes its parameter types and its impl's instance well-formed, like T ⊑ 'm for xs: 'm [T], as Rust's implied bounds do (check::implied_assumptions). The solver splits a type into the mutabilities it holds (Solver::solve_at_most), decides what only one choice meets, and keeps the rest. What's left when a group of functions is solved is about their types, and becomes their schemes' bounds; other unknowns are chosen to meet it, imm below first (Solver::settle_at_most). In a body with a complete signature, what's left about its parameters is an error (TypeError::NotAtMost), unless the function or its impl assumes it. A mutability that must be at most imm is decided right away, unless the function assumes a mutability is, which it could be too. A bound like T: imm or 'v: 'm lowers to Predicates::at_most (TypeRef::Mutability for the mutability on its own), the solver follows assumptions through 'v: 'm and 'm: imm (Solver::mutability_le), and a scheme carries them for its callers. A chosen impl's bounds are checked like its class predicates, and a struct's where a value is made.
    • A closure gets a new mutability, the types of the variables it uses from outside (ClosureFrame) are at most it, and a let mut one makes it Mut.
    • Once a body's types are resolved, check_deep_immutability reports each type with a mut array, struct or function inside an imm one, unless an "at most" error already did. The types that no body looks at are reported where they're written, the same way: those of a function without a body, like a class method, of a type alias, and of an impl's instance (written_type in boltlang-hir).

  • Defaulting (solve.rs): a mutability left over when a body is checked, and not generalized, becomes Imm. That happens after the errors are resolved, so that an undecided mutability is shown as [T] in them.

  • Showing types: mut T, imm T, 'm T for a named mutability, and T for a generalized or unknown one. TyNames gives a name to each generalized, unknown or hidden mutability that appears more than once. Schemes leave mutabilities out of their forall, and show a field constraint that's assigned to as mut a.x: b.

  • Tests: tests/checker/array_mutability.txt, tests/checker/struct_mutability.txt, tests/checker/named_mutability.txt, tests/checker/mutability_params.txt and tests/checker/closure_mutability.txt have a case for each rule on this page.

  • Proven: lean/ has a Lean proof, for a core of these rules with closures, structs and type parameters, that nothing reachable from an imm value ever changes, that a well-typed program never gets stuck, and that calling an imm function with imm arguments changes nothing that existed before. It includes the "at most" assumptions that #243 proposes, like T: imm, and proves the solver's shortcuts for them (Solver.lean): how it splits a type, when it can decide an unknown mutability right away, and that Solver::mutability_le finds every chain of assumptions.

  • Checked when running: every array and struct in the evaluator knows whether it was made mut or imm (Object::mutability). With Evaluator::with_mutability_checks, which the evaluator's tests and tests/run use, changing an imm one, or making an imm one that holds a mut one, stops with ErrorKind::MutabilityViolation. A program the type checker accepts never does, so a failure there is a bug in the checker. A closure isn't tagged, so an imm value holding a mut closure isn't caught there, but changing an imm array or struct through a closure is.

Vec[T] in std (#197) is a struct, so it gets a mutability like any other, and [T] is shorthand for it. So is a String in std (#199), with mut String taking the place of a separate StringBuilder.

Open questions​

  • A name used once says nothing that leaving it out doesn't, and could be a warning.
  • Impls for struct type constructors. impl Functor[Box] is for boxes of either mutability, so fmap must return a Box with the mutability of the one it's given, which it can't make: Box { item: f(b.item) } is imm. Higher-kinded types tie the mutability of the result to that of the argument, and what that should mean isn't decided.
  • Enums with a mutability, so that a variant can hold something that can be changed without a type parameter, and so that an enum can be changed in place.
  • Assigning to a field of a tuple through a field constraint, like fn f(t) { t.0 = 1; }, isn't checked: once the type is a tuple, it's a value, and the variable should be mut.

Prior art​

  • OCaml has no mut on variables. Whether a value can change is in its type: an array always can, a list never, and a record field only if it's declared mutable. Nothing is inferred, and nothing is deep.
  • Reference immutability, in Javari [Tschantz & Ernst 2005] and ReIm [Huang et al. 2012], puts a read-only qualifier on references in Java, and ReIm infers it. Javari's is deep, like imm, but a read-only reference can point at an object that others change. Here, Imm means that no one can.
  • Pony's reference capabilities [Clebsch et al. 2015] decide what each reference allows: iso (unique), val (can't be changed by anyone, deeply), ref (can be changed, and shared), and box (read-only, and either of the last two). imm is like val, mut like ref, and a parameter without either like box, which Pony gets by subtyping and Bolt by polymorphism. Pony makes val deep with viewpoint adaptation, where Bolt gives fields their struct's mutability and checks type parameters.
  • Modes in Jane Street's OCaml [Lorenzen et al. 2024] are qualifiers like unique and local, inferred alongside types. unique is what freezing without a copy would need.
