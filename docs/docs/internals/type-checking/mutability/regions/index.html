Regions

Proposal

Nothing on this page is implemented. It's a design for #209, which isn't decided yet. Regions only exist inside the type checker: a program never writes one, and the tutorial and the reference don't mention them.

Making a value that can't be changed from one that can​

A mut value can't become imm, since a mut name for it may still exist. Turning one into the other copies it:

fn freeze[T](xs: [T]) -> imm [T];    // a copy that can't be changed
fn thaw[T](xs: [T]) -> mut [T];      // a copy that can

Since imm is deep, freezing copies everything a value holds that's mut.

That's a copy for every value that's built step by step, since it has to be mut while it's built:

fn squares(n: i32) -> imm [i32] {
  let xs = mut [];
  for i in 0..n { xs.push(i * i); }
  xs          // error: expected `imm [i32]`, found `mut [i32]`
}

No one but squares has xs, so no one is left who could change it. But the checker can't tell: a mut value may have other names. In std, to_array, Vec.new and Vec.from_array have this problem, and so does fmap for Vec or Box (see the open questions).

What a region is​

A region is the mutability of values that a block makes and that nothing outside the block holds. A function's body and a closure's body are blocks too. This page writes a region as @r in code, and as rrr in equations:

μ::=Mut∣Imm∣α∣r\mu ::= \mathsf{Mut} \mid \mathsf{Imm} \mid \alpha \mid rμ::=Mut∣Imm∣α∣r
  • Inside the block, a region can be changed, like Mut.
  • When the block ends, it's free: nothing else has its values, so it becomes whatever the code around the block needs, Imm, Mut or a caller's 'm.

@ sets a region apart from a named mutability like 'm, which behaves the other way round:

'm@r
Comes froma signature: the caller chooses ita block: the checker finds it
In the blockmay be imm, so it can't be changedcan be changed
Outside the blockthe caller's mutabilitynothing has it

A region holds no information of its own: it's equal only to itself, and values are in it because unification put it in their types. It isn't a list of values, a count of references or an area of memory. When the program runs, a region is Mut.

So squares above type-checks: xs is @r [i32] in the body, and @r becomes the imm of the return type. Inside a function, a block does the same:

let ys: imm [i32] = {
  let xs = mut [];
  xs.push(1);
  xs              // `@r [i32]`, freed at the `}`
};

The rules​

1. Changing a value needs a mutability that can be changed: Mut, or a region. mut [1] and mut Point { .. } get a fresh mutability that must be changeable, rather than Mut, and it defaults to Mut. A function that changes its argument is generic over this, so that it takes regions too:

fn fill(xs, x) { xs[0] = x; }    // forall a. changeable 'm => fn('m [a], a) -> ()

2. A region is a changeable mutability that stays in its block. A mutability in the type of a block's value is a region of the block when it's still unknown once the enclosing function's body is solved, must be changeable, and appears in no type from outside the block: not in a variable from outside it, a parameter, a top-level variable, or an effect's operation. That's like the check that generalization makes before it generalizes a type variable.

3. A value leaves its region when its type meets one from outside. Then its mutability is no longer a region, and it stays Mut:

fn leak(log: mut [mut [i32]]) -> imm [i32] {
  let xs = mut [1];
  log.push(xs);     // `xs` is now `mut [i32]`, like the elements of `log`
  xs                // error: expected `imm [i32]`, found `mut [i32]`
}

The error should say why: "xs can't be imm, because it's stored in log here". It should describe the region rather than show @r, and showing it as mut would give "expected mut [i32], found mut [i32]".

4. A region can hold values from outside, but an imm value can't hold a region's. The "at most" order gets Imm⊑r\mathsf{Imm} \sqsubseteq rImm⊑r. What a region's values hold, like the B of a @r Vec[B], gives a constraint B⊑rB \sqsubseteq rB⊑r, which stays with the region and applies to whatever it becomes. r⊑Immr \sqsubseteq \mathsf{Imm}r⊑Imm is false, since an imm value would hold one that's still being changed. r⊑Mutr \sqsubseteq \mathsf{Mut}r⊑Mut can't happen, since a Mut value from outside would hold the region's, which rule 3 rules out.

5. A closure that captures a region's value has that region as its mutability, not just one that's at least the region. A closure's type doesn't show what it captured, so with "at least", a closure that also captures a mut value from outside would be a mut fn that could be stored outside, and still change the region's values. A let mut variable makes a closure changeable rather than Mut, so that a closure that counts in a block can be a region's too.

A region that a function type in the block's value has, directly, in a type argument or in a field of a struct, isn't freed: it stays changeable, and so Mut:

fn counter() -> (fn(), imm [i32]) {
  let xs = mut [0];
  (|| { xs[0] += 1; }, xs)    // error: expected `imm [i32]`, found `mut [i32]`
}

If xs became imm, calling the closure would still change it. Calling a function doesn't need it to be mut (deep imm), so this can't be left to the caller.

6. The block's value gets a fresh mutability for each of its regions. The constraints that rule 4 kept go with it, and "changeable" doesn't. What's around the block decides it, like for any unknown:

  • a let annotation, or what the value is used for later;
  • for a function's body, its declared return type, which is unified with the body's type only once the regions are known: so -> imm [i32] in squares meets a region rather than a Mut;
  • for an inferred function, the caller: fn squares(n) = ... is generalized to fn(i32) -> 'm [i32].

That changes what return types say for a body that makes a value with mut: fn buffer() = mut [0; 1024] would give whatever the caller asks for, rather than mut [u8].

A closure's type isn't generalized, so every call of a closure gives its result the same mutability. That's still sound: each call makes a new value, which only that call's result has.

Examples​

fmap for Vec gives the result whatever mutability the class asks for:

impl Functor[Vec] {
  fn fmap(f, xs) {
    let ys = mut [];
    for x in xs { ys.push(f(x)); }   // `B ⊑ @r`
    ys                               // `@r Vec[B]`, which can become any `'m Vec[B]` with `B ⊑ 'm`
  }
}

Calling f is fine, since f never sees ys. If B is mut, the result has to be mut too, as deep imm requires.

Box is the same: fn fmap(f, b) = mut Box { item: f(b.item) } gives a Box with the mutability of the one it's given.

Why every block​

Pony's recover [Clebsch et al. 2015] has to be written, because it restricts what its block may use: only what can be shared from outside. Every block doing that would reject ordinary code.

A region only looks at what leaves its block. When a value leaves, the region simply isn't one, and the value stays Mut, as it would be without regions. So freeing at a block only adds choices: a program that type-checks without regions still does with them, and blocks inside blocks compose, since a value freed in one flows on to the next. There's nothing to opt into, so no keyword is needed.

Region inference [Tofte & Talpin 1997] has to choose where regions go, since that decides when memory is freed, and its choices are hard to predict. Here, nothing is chosen: every block is a boundary.

A value can't be freed halfway through a block: in let xs = mut []; xs.push(1); let ys: imm [i32] = xs;, xs hasn't left anything. The part that builds it goes in a block of its own, as in the example in What a region is.

What regions don't do​

  • Changing a value's type in place, like an fmap_mut that turns a mut Vec[A] into a mut Vec[B]. That needs the caller to give up its name for the value, which is uniqueness: an affine type, or the unique mode of Jane Street's OCaml [Lorenzen et al. 2024].
  • Values that did leave their region still need freeze, which copies. With reference counting, freeze could skip the copy when the count is 1, as Koka and Lean do [Reinking et al. 2021].

Implementation​

A region isn't a new kind of type: it's an inference variable for a mutability, with a constraint that it's changeable. @r is how this page writes one that rule 2 found.

  • Solving: "changeable" is a constraint next to the at most ones. Solver::require_mut, for E0221, would add it instead of unifying with Mut. It's met by Mut and by a region, it fails on Imm and on a mutability parameter, and it defaults to Mut. A function's scheme carries it for an unknown that isn't in the result, like a 'm that must be changeable.
  • Closures: ClosureFrame unifies a closure's mutability with that of a changeable value it captures, instead of adding "at most".
  • Blocks: whether a block's mutabilities are regions depends on the rest of the function's body, which may give a variable from outside the block a type with one of them later on. So it's a deferred constraint between the type of the block's value and the type outside, decided once the body is solved: a region becomes a fresh mutability, and anything else is unified as now. For a function's body, the type outside is its declared return type. Only a mutability that must be changeable can be a region, so most blocks have nothing to decide.
  • Code generation: an instance can choose Imm for a region, and the block still changes those values before it ends. So a value made with mut must be allocated each time and stored by reference, never made a constant or stored by value as an imm one can be. That only becomes true once the block ends, which is what Sharing.lean would have to say.
  • The evaluator tags each array and struct with the mutability it was made with (Object::mutability). A value that becomes imm when its block ends is tagged Mut, so with_mutability_checks would stop on an imm value that holds it. The tag would have to change when the block ends.
  • Proof: the Lean proof doesn't cover regions. It would need rules 2 to 5, and the guarantee that a region's values can't be reached from outside while the block runs.

Open questions​

  • How a signature says that it takes a region. fn push[T](v: mut Vec[T], x: T) in std only takes Mut, so ys.push(…) on a region's value is an error. mut in a parameter could mean "changeable". But a function that stores its parameter where only Mut fits would then be an error, and would need another way to say that it wants exactly Mut:

    fn register(log: mut [mut [i32]], xs: mut [i32]) { log.push(xs); }

    Or a parameter could say "changeable" with a bound. Either changes many signatures in std.

  • What a freed mutability defaults to. One that nothing decides becomes Imm, like any unknown mutability. So let xs = { mut [] }; shows as imm [a], although it says mut. That's harmless, since nothing changes it, but defaulting a freed mutability to Mut would show what the code says.

  • Continuations. A handler that captures the rest of a block captures the region's values, like a closure. Resuming it after the block ended would change a value that may be imm by then. A mut continuation is resumed at most once, and a region's could be treated the same way.

Prior art​

  • Haskell's runST [Launchbury & Peyton Jones 1994] uses a type variable s in ST s and STRef s a as a region: the type of runST keeps an STRef s from leaving, so the result is pure. Here, the region is found when the block's body is solved, rather than written in a type.
  • Pony's recover [Clebsch et al. 2015] turns what a block makes into any capability, like iso or val, if the block only uses values from outside that can be shared. A region instead allows anything from outside, and checks what leaves, which is why it needs no keyword.
  • Region-based memory management [Tofte & Talpin 1997], in the ML Kit and Cyclone, is where the name comes from: there, a region is also an area of memory, freed when its block ends.
  • Rust's lifetimes are regions for references: where a reference is valid.
  • Perceus [Reinking et al. 2021] finds unique values at run time from their reference counts, and changes them in place.
