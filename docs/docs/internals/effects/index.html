Effects (design)

Not implemented

This page is a design. Nothing on it is implemented yet. Algebraic effects are tracked in #40.

An effect is something a function can do besides returning a value: waiting, failing, reading some state, logging. A function's type says which effects it can have, after does:

fn fetch(url: String) -> Response does Async;
fn crawl(url: String) -> () does Async + Log;

The async and reactive UI designs build on this page.

Declaring an effect​

An effect is declared with its operations, the functions that perform it:

effect Log {
    fn log(message: String);
}

effect State[S] {
    fn get() -> S;
    fn set(value: S);
}

An operation is called like any other function. Calling it gives the caller the effect: a function that calls log has Log in its type. A handler decides what an operation does, and takes the effect out of the type of the code it runs. The syntax of handlers is for another page.

Writing effects​

Effects come after the result type, after does, joined with +:

fn crawl(url: String) -> () does Async + Log { … }
fn count(xs: [String]) -> i32 does State[i32] = …;
fn total(xs: [i32]) -> i32 = …;
  • A written result type without does means the function has no effects, as in Koka [Leijen 2014]. If total called log, that would be an error at its signature.
  • A function without a written result type has its effects inferred, like its types (see Inferring effects).
  • The order doesn't matter: Async + Log and Log + Async are the same.
  • does comes before a body, = and where: fn f[T](x: T) -> T does Log where Show[T] = ….
  • In a function type, does is part of the type: f: fn(A) -> B does Log, n: i32. It belongs to the nearest fn, so fn(A) -> fn(B) -> C does Log is a function that returns a function with Log.

Function types follow the same rule: fn(A) -> B has no effects. So a parameter that takes a function with any effects needs an effect variable, as map has below.

The cost of this rule is that a new effect deep down a call chain, like a call of log, has to be added to each written signature above it. Signatures that are inferred, or that have an effect variable, don't need changing.

The effects after does are a row. + was chosen over a list in delimiters because there's nothing to close, so it can't be mixed up with a body (does { Async } { … }) or the , between parameters. It also reads like the bounds that Bolt already joins with +.

Effects with parameters​

An effect can have parameters, like State[S] above. Its arguments are fixed for the whole row: every get() of a State[i32] returns an i32.

An operation can have parameters of its own as well. Each call picks its own arguments, and the effect doesn't need a parameter for them:

effect Raise[E] {
    fn raise[T](error: E) -> T;
}

effect Async {
    fn suspend[T](start: fn(fn(T) -> ()) -> ()) -> T;
}

raise can stand where any type is expected, because it never returns, and every suspend waits for a value of a different type.

Parameters can be types, effects and mutabilities. Mutability parameters work as they do for structs.

Effect variables​

A function that takes a function as a parameter often has the effects of that function. An effect variable says so:

fn map[A, B, E](xs: [A], f: fn(A) -> B does E) -> [B] does E;

map([1, 2, 3], |x| x * 2);   // E is empty: no effects
map(urls, fetch);            // E is Async

So there's one map for every function, whatever it does. An effect variable is one more term in a row:

fn retry[T, E](times: i32, f: fn() -> T does E) -> T does Log + E;

retry has the effects of f and Log too. Nothing marks E as an effect variable: it's one because of where it's used, by the kind inference below.

A row has at most one effect variable. does E + F is an error, because there's no single way to split a row between two variables, and inference would have to guess. A function that needs both writes one variable, and its callers pass functions with the same effects.

No effect twice​

An effect can be in a row only once, even with different arguments:

fn f() does State[i32] + State[String];
//     error: `State` is in this row twice

Some languages allow this, like Koka, where the innermost handler of an effect wins and mask skips it. That's flexible, but hard to explain, and it makes inference guess which of the two a call means. So it's an error for now. Allowing it later won't break code that type-checks today. Code that needs two states can declare a second effect.

The rule holds for effect variables too. In does State[i32] + E, E can't contain State. A call that would put a second State in the row, like passing a function with State[String] for E, is an error at the call.

Kind inference​

Effects bring a new kind. The kinds are now:

κ::=Type∣Effect∣κ1→κ2\kappa ::= \mathsf{Type} \mid \mathsf{Effect} \mid \kappa_1 \to \kappa_2κ::=Type∣Effect∣κ1​→κ2​

Effect\mathsf{Effect}Effect is the kind of rows. A single effect is a row of one, so Log, State[i32] and Async + Log are all of kind Effect\mathsf{Effect}Effect. State is of kind Type→Effect\mathsf{Type} \to \mathsf{Effect}Type→Effect, so State alone isn't a row, as Option alone isn't a type. Koka has two kinds here, one for single effects and one for rows. With one, an effect variable can stand for any row, which is what map needs, and there's less to learn.

Kinds are still never written. Inference gets two new equations, next to those for types:

  1. Every term of a row after does is of kind Effect\mathsf{Effect}Effect.
  2. effect T[a_1, …, a_n] is of kind κa1→⋯→κan→Effect\kappa_{a_1} \to \dots \to \kappa_{a_n} \to \mathsf{Effect}κa1​​→⋯→κan​​→Effect, where the κai\kappa_{a_i}κai​​ come from the operations.

The rest is unchanged: an application T[τ1,…,τn]T[\tau_1, \dots, \tau_n]T[τ1​,…,τn​] gives κT=κτ1→⋯→κτn→β\kappa_T = \kappa_{\tau_1} \to \dots \to \kappa_{\tau_n} \to \betaκT​=κτ1​​→⋯→κτn​​→β, a parameter or field type is of kind Type\mathsf{Type}Type, and the equations are solved by unification.

An effect declaration is a group of its own, with its operations, like a class with its methods. So the kind of State's S comes from the types of get and set.

A parameter of an effect can be a row too:

effect Spawn[E] {
    fn spawn[T](task: fn() -> T does E) -> Task[T];
}

E is of kind Effect\mathsf{Effect}Effect, so Spawn is of kind Effect→Effect\mathsf{Effect} \to \mathsf{Effect}Effect→Effect, and Spawn[Async + Log] is a row.

Defaulting​

A kind variable that nothing decided becomes Type\mathsf{Type}Type, as before. An effect variable is always used after a does, so its kind is always decided, and it's never defaulted. That holds for the parameters of types and classes as well:

struct Button[E] { on_click: fn() -> () does E }

E is of kind Effect\mathsf{Effect}Effect from its use, so Button[Async] is a button whose click can wait.

Errors​

Kind errors are reported like they are now:

  • fn f(x: Log) expects a type and finds an effect: "expected a type of kind Type, found Log of kind Effect" (E0216).
  • fn f() does i32 expects an effect and finds a type: "expected a type of kind Effect, found i32 of kind Type".
  • fn f() does State misses an argument, like Option alone: "expected 1 type argument, found 0".
  • A parameter used both ways, like E in fn f[E](x: E) does E, takes the kind of its first use, and lowering reports the second.

Applications with an unknown head​

Kind inference allows a parameter of kind Type→Effect\mathsf{Type} \to \mathsf{Effect}Type→Effect, like the H in:

fn run[H, T](f: fn() -> T does H[T]) -> T;

But a row is unified by the names of its effects (see below), and H[T] has no name until H is known. So for now, every effect in a row has to be a known effect or an effect variable, and H[T] in a row is an error.

Unifying rows​

A row is a set of effects keyed by their name, plus at most one effect variable at the end, its tail: State[?a] + Log + ?e. Since no effect is in a row twice, unifying two rows is like unifying two records with their fields keyed by name [Rémy 1989, Gaster & Jones 1996]:

  1. An effect in both rows: unify their arguments. So State[?a] and State[i32] give ?a := i32, with no choice to make.
  2. An effect in only one row goes into the other row's tail. If that row has no tail, the rows don't match.
  3. When both have a tail, a fresh tail takes what's left of both.

For example:

State[α]+ϵ1≐Log+State[i32]+ϵ2⇝α:=i32, ϵ1:=Log+ϵ3, ϵ2:=ϵ3\mathsf{State}[\alpha] + \epsilon_1 \doteq \mathsf{Log} + \mathsf{State}[\mathsf{i32}] + \epsilon_2 \quad\leadsto\quad \alpha := \mathsf{i32},\ \epsilon_1 := \mathsf{Log} + \epsilon_3,\ \epsilon_2 := \epsilon_3State[α]+ϵ1​≐Log+State[i32]+ϵ2​⇝α:=i32, ϵ1​:=Log+ϵ3​, ϵ2​:=ϵ3​

A tail can't be given an effect that's already in its row. That's the rule against effects twice, and it does what an occurs check does for types: it keeps solutions finite and principal.

Inferring effects​

A body's effects are inferred like its types. The body starts with a fresh row variable, and each call adds the effects of what it calls. A handler takes its effect out.

Closures get their effects the same way: || fetch(x) is fn() -> Response does Async. A function without a written result type gets its effects generalized like its type variables, so it's polymorphic in what its callbacks do:

fn twice(f) { f(); f() }
twice: forall a e. fn(fn() -> a does e) -> a does e

Still to decide​

  • How to give does to the outer function of fn(A) -> fn(B) -> C. (T) is a one-element tuple type, so parentheses don't group types today.
  • The syntax and typing of handlers.
  • Effects twice in a row, if it turns out to be needed.
  • Applications like H[T] in a row.
