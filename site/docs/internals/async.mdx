# Async (design)

:::warning[Not implemented]
This page is a design sketch. **Nothing on it is implemented**: there are no
effects in Bolt yet, and `async` and `await` are reserved words without a
meaning. The syntax of effect types is that of the
[effects design](./effects.mdx).
:::

Code that waits, for a network request or a timer, is usually marked with
`async`, and its results are taken out of a future with `await`. With
algebraic effects, neither keyword is needed: code that can wait has the
`Async` effect in its type, and the compiler infers it like any other
effect. The [reactive UI design](./reactive.mdx) builds on this.

## Code that waits

A function that waits says so in its type, and returns its result directly:

```bolt
fn fetch(url: str) -> Result[Response, HttpError] does Async;

fn is_up(url: str) -> bool does Async = match fetch(url) {
    Ok(_) => true,
    Err(_) => false,
};
```

There's no `await`: `fetch` returns the response once it's there. Callers
don't write `async` either. A signature like `is_up`'s says `does Async`, as
it says its result type, and closures and functions without a written
result type get `Async` by inference.

The effect itself has two operations:

```bolt
effect Async {
    // Stop until `start` calls its callback with a value, then go on with it.
    fn suspend[T](start: fn(fn(T) -> ()) -> ()) -> T;
    // Run `task` next to the code that calls spawn.
    fn spawn[T](task: fn() -> T does Async) -> Task[T];
}

// Wait until a task is done, and get its result.
fn wait[T](task: Task[T]) -> T does Async;
```

`suspend` connects Bolt to the outside world: `fetch` calls the `fetch` of
the browser, and passes the callback of `suspend` to the promise it returns.
Most code never calls `suspend` or `spawn` itself.

## No function colours

In JavaScript and Rust, `async` spreads up the call chain, and a function
like `map` needs a second version for async callbacks. With effect
polymorphism, one `map` is enough: the effects of its callback become its
own.

```bolt
fn map[A, B, E](xs: [A], f: fn(A) -> B does E) -> [B] does E;

map([1, 2, 3], |x| x * 2);   // no effects
map(urls, is_up);            // does Async
```

An effect variable like `E` stands for a whole row of effects; the
[effects design](./effects.mdx#effect-variables) has the details.

## Running things at the same time

Without futures, code runs one step after the other:

```bolt
let a = fetch(x);   // waits for x
let b = fetch(y);   // and only then asks for y
```

To ask for both at once, `spawn` one of them, or use a function built on it:

```bolt
fn both[A, B](a: fn() -> A does Async, b: fn() -> B does Async) -> (A, B) does Async {
    let task = spawn(a);
    let result = b();
    (wait(task), result)
}

let (a, b) = both(|| fetch(x), || fetch(y));
```

So the common case reads like code that doesn't wait, and running things at
the same time is explicit. `Task[T]` is the only kind of future, for the
places where it's needed.

## One effect, many handlers

What waiting means depends on the handler that runs the code:

| Where                  | What the `Async` handler does                                  |
| ---------------------- | -------------------------------------------------------------- |
| An event handler       | runs it as a task of its own, next to the page                 |
| A component            | shows a fallback, and draws again once the data is there       |
| Rendering on a server  | waits for every request, then sends the page                   |
| A test                 | runs tasks one by one in a fixed order, with a fake clock      |

The code is the same in all of them. Tests in particular get easier: a
handler with a fake clock runs timers and timeouts right away, and always
in the same order.

## Cancelling

A task that isn't needed anymore should stop: a component that left the
page, or a search whose text changed. The handler of `Async` cancels it.

### The problem

A handler could cancel a task by never resuming it. With effects that's
allowed, since a continuation can be resumed once or not at all. But then
the rest of the task never runs, cleanup included:

```bolt
fn download(url: String) -> Bytes does Async {
    let conn = open(url);
    let data = conn.read_all();   // cancelled while it waits here
    conn.close();                 // never runs: the connection stays open
    data
}
```

### Unwinding a task

So the handler doesn't drop a task. It resumes it once more, with "you're
cancelled" instead of a value. The `suspend` the task waits in then stops,
like an error would, and the task unwinds from there up to the handler,
running its cleanup on the way. Nothing in the task runs after that.

A task is only cancelled while it waits, at a `suspend`. Code between two
waits always runs to the end, so this can't be cut off halfway:

```bolt
balance -= amount;
history.push(amount);
```

That's much easier to reason about than threads, which can be stopped
anywhere.

### `defer`

`defer` runs code when the block it's in ends, however it ends: normally,
by `return` or `break`, by an error, or by a cancel.

```bolt
fn download(url: String) -> Bytes does Async {
    let conn = open(url);
    defer conn.close();
    conn.read_all()
}
```

The `defer`s of a block run in the opposite order of their statements, so
what was opened last is closed first. `defer` keeps the cleanup next to
what it cleans up, which a `finally` doesn't, and Bolt has no `try` blocks
for one anyway. Go, Swift and Zig have `defer` too.

### `use`

A type that knows how to clean up can say so once, with a class:

```bolt
class Close[T] {
    fn close(self: mut T);
}
```

Then `use` is a `let` with the `defer` built in:

```bolt
fn download(url: String) -> Bytes does Async {
    use conn = open(url);   // let conn = open(url); defer conn.close();
    conn.read_all()
}
```

This is C#'s `using var` (with `IDisposable`) and Python's `with`. It's like
Rust's `Drop` in that the type writes the cleanup, but it runs where `use`
says, at the end of the block. Rust can drop values on its own because
every value has one owner. Bolt values can be shared, `let b = a` gives
the same connection a second name, so the end of `a`'s block can't know
that nobody uses it anymore. With `use`, the programmer says so. The
language server can warn about a value of a `Close` type that's bound with
`let`, as C#'s tools do for `IDisposable`.

### Still open

- **Catching a cancel.** Code that could catch "you're cancelled" could
  refuse to stop. Most designs let code see a cancel but not stop it.
- **Waiting in cleanup.** Closing a connection politely may need a network
  call, so a `defer` may want to wait, and then it can hang. C# has a
  separate `IAsyncDisposable` for this. Bolt could allow waiting in a
  `defer`, but with a time limit.
- **Blocks that can't be cancelled,** for steps that must finish together
  even though they wait, like a database commit.
- **Conduit.** Unwinding needs a way to resume a continuation with an
  unwind instead of values, which OCaml 5 calls `discontinue`. Conduit only
  has `resume` so far. Wasm stack switching has `resume_throw`, which does
  this.

## Compiling it

`Async` is the one effect that truly suspends, so code that performs it is
compiled differently: as a state machine or with a CPS transform, or with
the stack switching of wasm. `async` tells a compiler which functions those
are; effect types tell it the same, so nothing is lost.

Effect-polymorphic functions like `map` are harder: they may or may not
suspend, depending on their callback. They can be compiled twice, once for
each case, or always use stack switching. In the browser, JSPI lets wasm
wait for a promise of JavaScript, which is enough for `suspend` around
`fetch`.

## The keywords

The syntax reserves `async` and `await`. This design doesn't need them, so
they can be freed, or `await` can stay as another name for `wait`.

## Seeing where code waits

A call that can wait looks like any other call. That's the point, but
sometimes you want to know. The language server can mark these calls, with
a highlight or an inlay hint, like it can mark inferred
[reactive state](./reactive.mdx#inferring-state).

## Still to design

- What's still open about [cancelling](#still-open).
- Errors: `Result`, or an effect for failure that the handlers of `Async`
  know about, so that a failed task can fail the code that waits for it.
- Timeouts and racing, like `first(a, b)`, which need cancelling.
- Whether threads come later, and what `spawn` means then.
