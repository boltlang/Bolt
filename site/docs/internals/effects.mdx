# Effects (design)

:::warning[Not implemented]
This page is a design. **Nothing on it is implemented** yet. Algebraic
effects are tracked in [#40](https://github.com/boltlang/bolt/issues/40).
:::

An *effect* is something a function can do besides returning a value:
waiting, failing, reading some state, logging. A function's type says which
effects it can have, after `does`:

```bolt
fn fetch(url: String) -> Response does Async;
fn crawl(url: String) -> () does Async + Log;
```

The [async](./async.mdx) and [reactive UI](./reactive.mdx) designs build on
this page.

## Declaring an effect

An effect is declared with its *operations*, the functions that perform it:

```bolt
effect Log {
    fn log(message: String);
}

effect State[S] {
    fn get() -> S;
    fn set(value: S);
}
```

An operation is called like any other function, by its bare name, as class
methods are: `log("hi")`, `get()`. It's in scope wherever its effect is. If
two effects in scope have an operation of the same name, a call writes the
effect too: `State.get()`.

Calling an operation gives the caller the effect: a function that calls
`log` has `Log` in its type. A [handler](#handlers) decides what an
operation does, and takes the effect out of the type of the code it runs.

## Writing effects

Effects come after `does`, joined with `+`, after the result type if one
is written:

```bolt
fn crawl(url: String) -> () does Async + Log { … }
fn count(xs: [String]) -> i32 does State[i32] = …;
fn is_up(url: String) does Async = match fetch(url) { … };
fn total(xs: [i32]) -> i32 = …;
```

- The order doesn't matter: `Async + Log` and `Log + Async` are the same.
- `does` comes before a body, `=` and `where`:
  `fn f[T](x: T) -> T does Log where Show[T] = …`.
- In a function type, `does` is part of the type:
  `f: fn(A) -> B does Log, n: i32`. It belongs to the nearest `fn`, so
  `fn(A) -> fn(B) -> C does Log` is a function that returns a function with
  `Log`.

### Written or inferred

A function's effects are inferred only when neither its result type nor
`does` is written:

| Written                          | Result   | Effects         |
| -------------------------------- | -------- | --------------- |
| `fn f(x: i32) -> i32`            | `i32`    | none            |
| `fn f(x: i32) does Async`        | inferred | exactly `Async` |
| `fn f(x: i32) -> i32 does Async` | `i32`    | exactly `Async` |
| `fn f(x: i32)`                   | inferred | inferred        |

- A written result type without `does` means the function has no effects,
  as in Koka [Leijen 2014]. If `total` called `log`, that would be an error
  at its signature.
- A written `does` is all the function does, also when the result type is
  inferred. If `is_up` called `log`, that would be an error too. A function
  that has `Async` and whatever else its body does writes an effect
  variable: `does Async + E`.
- Without either, the effects are inferred like the types (see
  [Inferring effects](#inferring-effects)).

So a [complete signature](./type-checking/generalization.mdx), with every
type written, tells callers what the function does without its body.

Function types follow the same rule: `fn(A) -> B` has no effects. So a
parameter that takes a function with any effects needs an effect variable,
as `map` has [below](#effect-variables).

The cost of this rule is that a new effect deep down a call chain, like a
call of `log`, has to be added to each written signature above it.
Signatures that are inferred, or that have an effect variable, don't need
changing.

### `Nothing`

`Nothing` is the row without effects. It's for two places:

```bolt
fn double(x: i32) does Nothing = x * 2;   // no effects, result inferred
let b: Button[Nothing] = …;               // a button whose click does nothing
```

The first is the only way to say "no effects" without writing the result
type. The second gives an effect parameter no effects, like
`map[i32, i32, Nothing]`.

`Nothing` is a name of the prelude, of kind `Effect`, and capitalized like
other effects. It isn't an effect without operations: `Nothing + E` is `E`,
and `does Nothing + Log` is `does Log`, which the formatter writes instead. It was chosen over
`none`, which is too close to `Option`'s `None`, and over `()`, which is the unit type. A modifier like
Koka's `total` or a `pure fn` would be a second place to write effects, and
couldn't be a type argument.

The effects after `does` are a *row*. `+` was chosen over a list in
delimiters because there's nothing to close, so it can't be mixed up with a
body (`does { Async } { … }`) or the `,` between parameters. It also reads
like the bounds that Bolt already joins with `+`.

## Effects with parameters

An effect can have parameters, like `State[S]` above. Its arguments are
fixed for the whole row: every `get()` of a `State[i32]` returns an `i32`.

An operation can have parameters of its own as well. Each call picks its own
arguments, and the effect doesn't need a parameter for them:

```bolt
effect Raise[E] {
    fn raise[T](error: E) -> T;
}

effect Async {
    fn suspend[T](start: fn(fn(T) -> ()) -> ()) -> T;
}
```

`raise` can stand where any type is expected, because it never returns, and
every `suspend` waits for a value of a different type.

Parameters can be types, effects and mutabilities. Mutability parameters
work as they do for structs.

## Effect variables

A function that takes a function as a parameter often has the effects of
that function. An *effect variable* says so:

```bolt
fn map[A, B, E](xs: [A], f: fn(A) -> B does E) -> [B] does E;

map([1, 2, 3], |x| x * 2);   // E is Nothing
map(urls, fetch);            // E is Async
```

So there's one `map` for every function, whatever it does. An effect
variable is one more term in a row:

```bolt
fn retry[T, E](times: i32, f: fn() -> T does E) -> T does Log + E;
```

`retry` has the effects of `f` and `Log` too. Nothing marks `E` as an effect
variable: it's one because of where it's used, by the kind inference below.

A row has at most one effect variable. `does E + F` is an error, because
there's no single way to split a row between two variables, and inference
would have to guess. A function that needs both writes one variable, and its
callers pass functions with the same effects.

## No effect twice

An effect can be in a row only once, even with different arguments:

```bolt
fn f() does State[i32] + State[String];
//     error: `State` is in this row twice
```

Some languages allow this, like Koka, where the innermost handler of an
effect wins and `mask` skips it. That's flexible, but hard to explain, and it
makes inference guess which of the two a call means. So it's an error for
now. Allowing it later won't break code that type-checks today. Code that
needs two states can declare a second effect.

The rule holds for effect variables too. In `does State[i32] + E`, `E` can't
contain `State`. A call that would put a second `State` in the row, like
passing a function with `State[String]` for `E`, is an error at the call.

## Handlers

A handler is a `match` with `effect` arms, as in OCaml 5
[Sivaramakrishnan et al. 2021]. The `match` runs its scrutinee under the
handler:

```bolt
effect Yield {
    fn yield(value: i32);
}

fn sum(body: fn() does Yield) -> i32 =
    match body() {
        () => 0,
        effect yield(x), k => x + resume(k, ()),
    };
```

- **Value arms**, like `() => 0`, match what the scrutinee returns when
  it's done, as in any `match`. They're what Koka and OCaml call the return
  clause.
- **Effect arms**, like `effect yield(x), k => …`, match an operation and
  its arguments, with ordinary patterns. `k` is the *continuation*: the rest
  of the scrutinee, paused where it performed the operation.
- **`resume(k, v)`** continues the scrutinee with `v` as the result of the
  operation. It returns what the whole `match` gives for the rest of the
  scrutinee. So `x + resume(k, ())` adds `x` to the sum of what's yielded
  after it, and the value arm gives `0` at the end. There's no mutable state.

Handlers are *deep*: after a `resume`, the rest of the scrutinee is still
handled by the same `match`. An arm itself isn't, so an operation performed
in an arm goes to the next handler out.

### Not resuming

An arm that doesn't resume *aborts*: the scrutinee never continues, and the
arm's value is the value of the `match`. That's how exceptions work:

```bolt
effect Raise[E] {
    fn raise[T](error: E) -> T;
}

fn catch[T, E, R](body: fn() -> T does Raise[E] + R) -> Result[T, E] does R =
    match body() {
        value => Ok(value),
        effect raise(error), _ => Err(error),
    };
```

### Keeping the continuation

`k` is a value like any other. It can be kept and resumed later, which is
what a scheduler does:

```bolt
match main() {
    () => run_next(queue),
    effect suspend(start), k => {
        start(|value| queue.push(|| resume(k, value)));
        run_next(queue)
    },
}
```

A continuation can be resumed **once**. Resuming it again stops the program,
as in Conduit, whose continuations are one-shot because the code they run
can change things, and running those changes twice would be wrong.

### State

With the value arm, state can be a function that each arm passes on:

```bolt
fn run_state[S, T, R](init: S, body: fn() -> T does State[S] + R) -> (T, S) does R {
    let f = match body() {
        value => |s| (value, s),
        effect get(), k => |s| resume(k, s)(s),
        effect set(s), k => |_| resume(k, ())(s),
    };
    f(init)
}
```

A `let mut` variable that the arms change is simpler, and works as well:

```bolt
fn run_state[S, T, R](init: S, body: fn() -> T does State[S] + R) -> (T, S) does R {
    let mut state = init;
    let value = match body() {
        value => value,
        effect get(), k => resume(k, state),
        effect set(s), k => { state = s; resume(k, ()) },
    };
    (value, state)
}
```

### Every operation needs an arm

A `match` that has an arm for an operation of an effect handles that whole
effect, and must have arms for all its operations:

```text
error: this `match` handles `State`, but has no arm for `set`
```

Otherwise the effect couldn't leave the row, and whether it does would
depend on whether an arm was forgotten. To handle one operation and pass
another on to the next handler out, the arm performs it again:

```bolt
match body() {
    value => value,
    effect get(), k => { log("get"); resume(k, get()) },
    effect set(s), k => resume(k, set(s)),
}
```

The arms run outside of the `match`, so the `get()` and `set(s)` in them
go to the next handler, and the `match` still has `State` in its row. Arms
like these always resume at the end, so Conduit compiles them to plain
calls. A shorthand for passing on the rest is discussed in
[#347](https://github.com/boltlang/bolt/issues/347).

The arms of each operation must be exhaustive, like value arms:
`effect yield(0), k` alone doesn't handle `yield(1)`.

### Names

An arm names its operation by its bare name. When the effects of a `match`
have two operations of the same name, the arm writes the effect too:
`effect State.get(), k`.

### Typing

Say the scrutinee has type $T$ and does $\mathit{Op}_1 + \dots + \rho$,
where the $\mathit{Op}_i$ are the effects with arms, and the `match` has
type $U$:

- The value arms have patterns of type $T$, and must be exhaustive.
- An arm for an operation `fn op(a: A) -> B` of $\mathit{Op}_i$ has patterns
  of type $A$, and binds `k` to a `Cont[B, U, R]`, where `R` is $\rho$:
  what resuming the continuation does. `R` is of kind $\mathsf{Effect}$.
- `resume(k, b)` has type $U$ and does $\rho$.
- The `match` does $\rho$, plus what its arms do.

So `match` takes the effects it has arms for out of the row, and nothing
else.

An operation with type parameters of its own, like `fn suspend[T](…) -> T`,
gives each of its arms a new type for `T`, equal to no other type. In the
scheduler above, `k` can only be resumed with a value of that type, which
only `start` provides. Existential types of GADTs are checked the same way.

### Lowering

A `match` with effect arms becomes a `handle` in Conduit:

- the scrutinee becomes the body closure, through lambda lifting;
- the value arms become the return clause;
- the arms of each operation become its clause, with a decision graph over
  the arguments.

### Why `match`

A handler could also be a `handle { … } with { fn yield(x) { … } }` block,
as in Effekt, or a declaration like `impl`. `match` was chosen because it
has a return clause, its value arms, and matches the arguments of
operations with patterns, with the exhaustiveness checks and decision
graphs that Bolt already has. It also reads like handling exceptions. The
cost is that a `match` that only handles effects still needs a value arm
like `v => v`, and `, k` is a form that nothing else in Bolt has.

## Kind inference

Effects bring a new kind. The [kinds](./type-checking/kinds.mdx) are now:

$$
\kappa ::= \mathsf{Type} \mid \mathsf{Effect} \mid \kappa_1 \to \kappa_2
$$

$\mathsf{Effect}$ is the kind of rows. A single effect is a row of one, so
`Log`, `State[i32]` and `Async + Log` are all of kind $\mathsf{Effect}$.
`State` is of kind $\mathsf{Type} \to \mathsf{Effect}$, so `State` alone
isn't a row, as `Option` alone isn't a type. Koka has two kinds here, one
for single effects and one for rows. With one, an effect variable can stand
for any row, which is what `map` needs, and there's less to learn.

Kinds are still never written. Inference gets two new equations, next to
those for types:

1. Every term of a row after `does` is of kind $\mathsf{Effect}$.
2. `effect T[a_1, …, a_n]` is of kind
   $\kappa_{a_1} \to \dots \to \kappa_{a_n} \to \mathsf{Effect}$,
   where the $\kappa_{a_i}$ come from the operations.

The rest is unchanged: an application $T[\tau_1, \dots, \tau_n]$ gives
$\kappa_T = \kappa_{\tau_1} \to \dots \to \kappa_{\tau_n} \to \beta$, a
parameter or field type is of kind $\mathsf{Type}$, and the equations are
solved by unification.

An effect declaration is a group of its own, with its operations, like a
class with its methods. So the kind of `State`'s `S` comes from the types of
`get` and `set`.

For the `map` above:

| Parameter | Used as             | Kind                 |
| --------- | ------------------- | -------------------- |
| `A`       | `[A]`, `fn(A)`      | $\mathsf{Type}$      |
| `B`       | `-> B`, `[B]`       | $\mathsf{Type}$      |
| `E`       | `does E`            | $\mathsf{Effect}$    |

A parameter of an effect can be a row too:

```bolt
effect Spawn[E] {
    fn spawn[T](task: fn() -> T does E) -> Task[T];
}
```

`E` is of kind $\mathsf{Effect}$, so `Spawn` is of kind
$\mathsf{Effect} \to \mathsf{Effect}$, and `Spawn[Async + Log]` is a row.

### Defaulting

A kind variable that nothing decided becomes $\mathsf{Type}$, as before.
An effect variable is always used after a `does`, so its kind is always
decided, and it's never defaulted. That holds for the parameters of types
and classes as well:

```bolt
struct Button[E] { on_click: fn() -> () does E }
```

`E` is of kind $\mathsf{Effect}$ from its use, so `Button[Async]` is a
button whose click can wait.

### Errors

Kind errors are reported like they are now:

- `fn f(x: Log)` expects a type and finds an effect: "expected a type of
  kind `Type`, found `Log` of kind `Effect`" (`E0216`).
- `fn f() does i32` expects an effect and finds a type: "expected a type of
  kind `Effect`, found `i32` of kind `Type`".
- `fn f() does State` misses an argument, like `Option` alone: "expected 1
  type argument, found 0".
- A parameter used both ways, like `E` in `fn f[E](x: E) does E`, takes the
  kind of its first use, and lowering reports the second.

### Applications with an unknown head

Kind inference allows a parameter of kind
$\mathsf{Type} \to \mathsf{Effect}$, like the `H` in:

```bolt
fn run[H, T](f: fn() -> T does H[T]) -> T;
```

But a row is unified by the names of its effects (see below), and `H[T]`
has no name until `H` is known. So for now, every effect in a row has to be
a known effect or an effect variable, and `H[T]` in a row is an error.

## Unifying rows

A row is a set of effects keyed by their name, plus at most one effect
variable at the end, its *tail*: `State[?a] + Log + ?e`. Since no effect is
in a row twice, unifying two rows is like unifying two records with their
fields keyed by name [Rémy 1989, Gaster & Jones 1996]:

1. An effect in both rows: unify their arguments. So `State[?a]` and
   `State[i32]` give `?a := i32`, with no choice to make.
2. An effect in only one row goes into the other row's tail. If that row
   has no tail, the rows don't match.
3. When both have a tail, a fresh tail takes what's left of both.

For example:

$$
\mathsf{State}[\alpha] + \epsilon_1 \doteq \mathsf{Log} + \mathsf{State}[\mathsf{i32}] + \epsilon_2
\quad\leadsto\quad
\alpha := \mathsf{i32},\ \epsilon_1 := \mathsf{Log} + \epsilon_3,\ \epsilon_2 := \epsilon_3
$$

A tail can't be given an effect that's already in its row. That's the rule
against effects twice, and it does what an occurs check does for types: it
keeps solutions finite and principal.

## Inferring effects

A body's effects are inferred like its types. The body starts with a fresh
row variable, and each call adds the effects of what it calls. A `match`
with effect arms takes the effects it handles out.

Closures get their effects the same way: `|| fetch(x)` is
`fn() -> Response does Async`. A function without a written result type gets its
effects generalized like its type variables, so it's polymorphic in what
its callbacks do:

```bolt
fn twice(f) { f(); f() }
```

```text
twice: forall a e. fn(fn() -> a does e) -> a does e
```

## Still to decide

- How to give `does` to the outer function of `fn(A) -> fn(B) -> C`. `(T)`
  is a one-element tuple type, so parentheses don't group types today.
- A shorthand for passing operations on in a handler
  ([#347](https://github.com/boltlang/bolt/issues/347)).
- `discontinue(k)`, to unwind a continuation instead of resuming it, for
  [cancelling](./async.mdx#cancelling).
- `match { … } { … }`, with a block as scrutinee: Bolt has record literals
  in braces, so the parser has to tell the two apart.
- Effects twice in a row, if it turns out to be needed.
- Applications like `H[T]` in a row.
