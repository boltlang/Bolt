# Regions

:::info[Proposal]
Nothing on this page is implemented. It's a design for
[#209](https://github.com/boltlang/Bolt/issues/209), which isn't decided
yet. Regions only exist inside the type checker: a program never writes
one, and the tutorial and the reference don't mention them.
:::

## Making a value that can't be changed from one that can

A `mut` value can't become `imm`, since a `mut` name for it may still
exist. Turning one into the other copies it:

```bolt
fn freeze[T](xs: [T]) -> imm [T];    // a copy that can't be changed
fn thaw[T](xs: [T]) -> mut [T];      // a copy that can
```

Since `imm` is deep, freezing copies everything a value holds that's `mut`.

That's a copy for every value that's built step by step, since it has to
be `mut` while it's built:

```bolt
fn squares(n: i32) -> imm [i32] {
  let xs = mut [];
  for i in 0..n { xs.push(i * i); }
  xs          // error: expected `imm [i32]`, found `mut [i32]`
}
```

No one but `squares` has `xs`, so no one is left who could change it. But
the checker can't tell: a `mut` value may have other names. In `std`,
`to_array`, `vec_new` and `vec_from_array` have this problem, and so does
`fmap` for `Vec` or `Box` (see the [open questions](./index.mdx#open-questions)).

## Regions

A *region* is the mutability of values that a function body makes and
that nothing outside the body holds. This page writes one as `@r` in
code, and as $r$ in equations:

$$
\mu ::= \mathsf{Mut} \mid \mathsf{Imm} \mid \alpha \mid r
$$

- **Inside the body, a region can be changed**, like `Mut`.
- **When the body ends, it's free**: nothing else has its values, so it
  becomes whatever the caller needs, `Imm`, `Mut` or a caller's `'m`.

`@` sets a region apart from a [named mutability](./names.mdx) like `'m`,
which behaves the other way round:

| | `'m` | `@r` |
|---|---|---|
| Comes from | a signature: the caller chooses it | a body: the checker finds it |
| In the body | may be `imm`, so it can't be changed | can be changed |
| Outside the body | the caller's mutability | nothing has it |

A region holds no information of its own: it's equal only to itself, and
values are in it because unification put it in their types. It isn't a
list of values, a count of references or an area of memory. When the
program runs, a region is `Mut`.

So `squares` above type-checks: `xs` is `@r [i32]` in the body, and `@r`
becomes the `imm` of the return type.

## The rules

**1. Changing a value needs a mutability that can be changed**: `Mut`, or
a region. `mut [1]` and `mut Point { .. }` get a fresh mutability that must
be changeable, rather than `Mut`, and it defaults to `Mut`. A function that
changes its argument is generic over this, so that it takes regions too:

```bolt
fn fill(xs, x) { xs[0] = x; }    // forall a. changeable 'm => fn('m [a], a) -> ()
```

**2. A region is a changeable mutability that stays in the body.** Once a
body is solved, a mutability is a region when it's still unknown, must be
changeable, and appears in no type from outside the body: not in a
parameter, a variable it captures, a top-level variable, or an effect's
operation. That's the check that
[generalization](../generalization.mdx) makes before it generalizes a
type variable. Only regions in the result matter: one that isn't in the
result defaults to `Mut`, as now.

**3. A value leaves its region when its type meets one from outside.**
Then its mutability is no longer a region, and it stays `Mut`:

```bolt
fn leak(log: mut [mut [i32]]) -> imm [i32] {
  let xs = mut [1];
  log.push(xs);     // `xs` is now `mut [i32]`, like the elements of `log`
  xs                // error: expected `imm [i32]`, found `mut [i32]`
}
```

The error should say why: "`xs` can't be `imm`, because it's stored in
`log` here". It should describe the region rather than show `@r`, and
showing it as `mut` would give "expected `mut [i32]`, found `mut [i32]`".

**4. A region can hold values from outside, but an `imm` value can't hold
a region's.** The "at most" order gets `imm ⊑ @r`. What a region's values
hold, like the `B` of a `@r Vec[B]`, gives a constraint `B ⊑ @r`, which
stays with the region and applies to whatever it becomes. `@r ⊑ imm` is
false, since an `imm` value would hold one that's still being changed.
`@r ⊑ Mut` can't happen, since a `Mut` value from outside would hold the
region's, which rule 3 rules out.

**5. A closure that captures a region's value has that region as its
mutability**, not just one that's at least the region. A closure's type
doesn't show what it captured, so with "at least", a closure that also
captures a `mut` value from outside would be a `mut fn` that could be
stored outside, and still change the region's values. A `let mut` variable
makes a closure changeable rather than `Mut`, so that a closure that
counts in a body can be a region's too.

A region that a function type in the result has, directly, in a type
argument or in a field of a struct, isn't freed: it stays changeable, and
so `Mut`:

```bolt
fn counter() -> (fn(), imm [i32]) {
  let xs = mut [0];
  (|| { xs[0] += 1; }, xs)    // error: expected `imm [i32]`, found `mut [i32]`
}
```

If `xs` became `imm`, calling the closure would still change it. Calling a
function doesn't need it to be `mut` ([deep `imm`](./deep.mdx)), so this
can't be left to the caller.

**6. A declared return type is unified with the body's type only after
the body's regions are known.** So `-> imm [i32]` in `squares` meets an
unknown, changeable mutability that turns out to be a region, rather than
a `Mut`. An inferred function is generalized over its regions:
`fn squares(n) = ...` is `fn(i32) -> 'm [i32]`, with `'m` chosen by each
caller. That changes what [return types](./functions.mdx#return-types)
say for a body that makes a value with `mut`: `fn buffer() = mut [0; 1024]`
would give whatever the caller asks for, rather than `mut [u8]`.

## Examples

`fmap` for `Vec` gives the result whatever mutability the class asks for:

```bolt
impl Functor[Vec] {
  fn fmap(f, xs) {
    let ys = mut [];
    for x in xs { ys.push(f(x)); }   // `B ⊑ @r`
    ys                               // `@r Vec[B]`, which can become any `'m Vec[B]` with `B ⊑ 'm`
  }
}
```

Calling `f` is fine, since `f` never sees `ys`. If `B` is `mut`, the
result has to be `mut` too, as deep `imm` requires.

`Box` is the same: `fn fmap(f, b) = mut Box { item: f(b.item) }` gives a
`Box` with the mutability of the one it's given.

## Why only function bodies

A region could start and end anywhere in a body, but finding the best
places is region inference [Tofte & Talpin 1997], and its answers are hard
to predict. A function has one boundary that's easy to see, and its
signature already says what it gives: a result whose mutability the
caller chooses is a value that's new.

A body that wants to free a value halfway can move that part into a
function of its own. If that's often needed, a block like Pony's
`recover { ... }` could do the same inside a body, with the same rules.

A closure isn't a boundary: its type isn't generalized, so its result
can't have a mutability that each call chooses.

## What regions don't do

- **Changing a value's type in place**, like an `fmap_mut` that turns a
  `mut Vec[A]` into a `mut Vec[B]`. That needs the caller to give up its
  name for the value, which is uniqueness: an affine type, or the `unique`
  mode of Jane Street's OCaml [Lorenzen et al. 2024].
- **Values that did leave their region** still need `freeze`, which
  copies. With reference counting, `freeze` could skip the copy when the
  count is 1, as Koka and Lean do [Reinking et al. 2021].

## Implementation

A region isn't a new kind of type: it's an inference variable for a
mutability, with a constraint that it's changeable. `@r` is how this page
writes one that rule 2 found.

- **Solving**: "changeable" is a constraint next to the
  [at most](./deep.mdx) ones. `Solver::require_mut`, for E0221, would add
  it instead of unifying with `Mut`. It's met by `Mut` and by a region, it
  fails on `Imm` and on a mutability parameter, and it defaults to `Mut`.
  A function's scheme carries it for an unknown that isn't in the result,
  like a `'m` that must be changeable.
- **Closures**: `ClosureFrame` unifies a closure's mutability with that of
  a changeable value it captures, instead of adding "at most".
- **Bodies**: `infer_body` checks a body against a fresh return type,
  finds its regions once it's solved, drops their "changeable", and only
  then unifies with the declared return type.
- **Code generation**: an instance can choose `Imm` for a region, and the
  body still changes those values before it returns. So a value made with
  `mut` must be allocated each time and stored by reference, never made a
  constant or stored by value as an `imm` one can be. That only becomes
  true once the body returns, which is what `Sharing.lean` would have to
  say.
- **The evaluator** tags each array and struct with the mutability it was
  made with (`Object::mutability`). A value that becomes `imm` when its
  body returns is tagged `Mut`, so `with_mutability_checks` would stop on
  an `imm` value that holds it. The tag would have to change when the body
  returns.
- **Proof**: the Lean proof doesn't cover regions. It would need rules 2
  to 5, and the guarantee that a region's values can't be reached from
  outside while the body runs.

## Open questions

- **How a signature says that it takes a region.**
  `fn push[T](v: mut Vec[T], x: T)` in `std` only takes `Mut`, so
  `ys.push(…)` on a region's value is an error. `mut` in a parameter
  could mean "changeable". But a function that stores its parameter where
  only `Mut` fits, would then be an error, and would need another way to
  say that it wants exactly `Mut`:

  ```bolt
  fn register(log: mut [mut [i32]], xs: mut [i32]) { log.push(xs); }
  ```

  Or a parameter could say
  "changeable" with a bound. Either changes many signatures in `std`.
- **Continuations.** A handler that captures the rest of a body captures
  the region's values, like a closure. Resuming it after the body returned
  would change a value that may be `imm` by then. A
  [`mut` continuation](../../reactive.mdx) is resumed at most once, and a
  region's could be treated the same way.
- **A `recover` block**, if moving code into a function turns out to be
  too often needed.

## Prior art

- **Haskell's `runST`** [Launchbury & Peyton Jones 1994] uses a type
  variable `s` in `ST s` and `STRef s a` as a region: the type of `runST`
  keeps an `STRef s` from leaving, so the result is pure. Here, the region
  is found by generalization rather than written in a type.
- **Pony's `recover`** [Clebsch et al. 2015] turns what a block makes into
  any capability, like `iso` or `val`, if the block only uses values from
  outside that can be shared. A region instead allows anything from
  outside, and checks what leaves.
- **Region-based memory management** [Tofte & Talpin 1997], in the ML Kit
  and Cyclone, is where the name comes from: there, a region is also an
  area of memory, freed when its block ends.
- **Rust's lifetimes** are regions for references: where a reference is
  valid.
- **Perceus** [Reinking et al. 2021] finds unique values at run time from
  their reference counts, and changes them in place.
