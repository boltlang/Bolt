# Mutability

:::warning[Not compiled yet]
The type checker and the evaluator implement this page
([#195](https://github.com/boltlang/Bolt/issues/195)). The code generator
doesn't compile arrays or structs yet: see
[#177](https://github.com/boltlang/Bolt/issues/177) and
[#179](https://github.com/boltlang/Bolt/issues/179). The design was decided
in [#196](https://github.com/boltlang/Bolt/issues/196).
:::

Arrays and structs are *shared*: `let ys = xs` makes `ys`
another name for the same array, and `let q = p` another name for the same
struct, as in JavaScript, Java and OCaml. Passing one to a function passes
a pointer, and a function can fill in what it's given.

Sharing breaks what `mut` on a variable promises:

```bolt
let mut xs = [1, 2];
let ys = xs;     // not `mut`
xs[0] = 9;
ys[0];           // 9: `ys` changed anyway
```

This chapter describes how the type checker keeps a promise that sharing
can't break. **Whether an array or a struct can be changed is part of its
type**, and every name for it has the same type, so they all agree.

## Arrays and structs have a mutability

The type of an array or a struct has a *mutability*, which is `Mut` or
`Imm`:

$$
[\tau] \;=\; \mathsf{Array}[\mu, \tau] \qquad
S[\tau_1, \ldots, \tau_n]^\mu \qquad
\mu ::= \mathsf{Mut} \mid \mathsf{Imm} \mid \alpha
$$

`Mut` and `Imm` are types of their own [kind](../kinds.mdx). A mutability
can be an inference variable, like any type, and it's unified and
generalized like one. That's all the type checker needs: no subtyping, and
no new kind of constraint. A struct's mutability isn't one of its type
arguments, so it doesn't change its kind: `Box` is still of kind
$\mathsf{Type} \to \mathsf{Type}$.

In source code, and when types are shown:

| Written | Means |
|---|---|
| `mut [i32]`, `mut Point` | can be changed |
| `imm [i32]`, `imm Point` | can never be changed, by anyone |
| `[i32]`, `Point` | either: see [annotations](./functions.mdx#annotations) |

Only arrays and structs have a mutability. An enum can't be changed in
place: `match` gives the values of its fields, and there's no way to
assign to one. A tuple is still a value, copied when it's assigned, so
`t.0 = 1` needs `let mut t` as before. `mut` before anything else, like
`mut i32` or `mut Option[i32]`, is an error (E0222).

Something can be changed only if its type is `mut`:

```bolt
fn push[T](xs: mut [T], x: T);    // in `std`

let xs = mut [1, 2];
xs.push(3);      // fine
xs[0] = 9;       // fine

let p = mut Point { x: 0, y: 0 };
p.x = 5;         // fine

let ys = [1, 2];
ys[0] = 9;       // error: `ys` is `imm [i32]`, which can't be changed
```

Assigning to an element, `xs[i] = e`, needs `xs` to be a `mut` array, and
assigning to a field, `p.x = e`, needs `p` to be a `mut` struct. So does
calling a function whose parameter is `mut`, like `push`. What decides is
the innermost array or struct of the place that's assigned to: in
`l.a.x = 1`, it's `l.a`, and in `xs[0].x = 1`, it's `xs[0]`.

## Where the mutability comes from

**The expression that makes an array or a struct decides** whether it can
be changed. Variables only pass it on:

- `[1, 2]` and `Point { x: 0, y: 0 }` can't be changed: `imm [i32]` and
  `imm Point`.
- `mut [1, 2]`, `mut []`, `mut Point { x: 0, y: 0 }` and, for a tuple
  struct, `mut Meters(1.0)` can be changed.
- A function's result has the mutability of its type: `Vec.new()` could
  return `mut [T]`, and `xs.copy()` a new `mut [T]`.
- `mut` before a variant, like `mut Shape.Circle { radius: 1.0 }`, or before
  the call of a function, is an error (E0222).

`let mut` no longer has anything to do with the contents of an array or a
struct. It only means the variable can be assigned again:

```bolt
let xs = mut [1];
xs.push(2);         // fine: the array is `mut`
xs = mut [3];       // error: `xs` isn't `mut`

let mut ys = [1];
ys = [2, 3];        // fine: the variable is `mut`
ys.push(4);         // error: the array isn't
```

## Aliases share the mutability

`let ys = xs` unifies the types of `ys` and `xs`, mutability included. So an
alias of a `mut` array or struct is `mut` too, without saying so:

```bolt
let xs = mut [1, 2];
let ys = xs;        // `mut [i32]`, like `xs`
ys.push(3);         // fine, and `xs` sees it
```

Since this is unification, it works however the alias is made: through a
function, a branch, a struct or a closure.

```bolt
fn id(x) = x;

let a = id(xs);                         // `mut [i32]`
let b = if c { xs } else { mut [] };    // `mut [i32]`
let get = || xs;                        // `mut fn() -> mut [i32]`
```

An alias can't change the mutability. Unifying `Mut` with `Imm` is an error:

```bolt
let xs = mut [1, 2];
let ys: imm [i32] = xs;   // error: expected `imm [i32]`, found `mut [i32]`
```

`S { ..base }` copies the fields it doesn't give from `base`, so it can
make a struct of another mutability from it, like a `mut Point` from an
`imm` one. But the copy is shallow: an array, struct or function in a field
is shared with `base`, which would make it an alias with another
mutability. So when a field that's copied holds one with the struct's own
mutability, `base` must have the same mutability as the struct:

```bolt
let q = mut Point { ..p };   // fine, whatever `p` is: the fields are numbers
let l = mut Line { a: mut Point { x: 1, y: 2 }, b: mut Point { x: 3, y: 4 } };
Line { ..l }                 // error: expected `imm Line`, found `mut Line`
Line { a: Point { x: 0, y: 0 }, b: Point { x: 0, y: 0 }, ..l }   // fine: nothing is copied
```

## Deep `imm`

**What an `imm` value holds can't be changed either.** Otherwise an
`imm Line` could hold a `mut Point`, and the line would change after all.
The [tutorial](../../../tutorial/advanced/mutability.mdx) shows the rules
from a user's side; this section is about how the checker applies them.

**A field has the mutability of its struct.** An array or struct in a
field without `mut` or `imm` has the struct's own mutability, which is a
hidden parameter of the struct: `struct Line { a: Point, b: Point }` is
`Line^m` with `a: Point^m`. A field can be `imm`, but not `mut` (E0224),
since a `mut` field in an `imm` struct would break the rule. The fields of
an enum, which has no mutability, are `imm`.
([#271](https://github.com/boltlang/Bolt/issues/271): in a field like
`imm [Point]`, the `Point` gets the struct's mutability too, so the struct
can only be `imm`.)

**An `imm` value can't hold a `mut` one through a type parameter**
(E0223): `Box { item: mut Point { .. } }` is an `imm Box[mut Point]`. What
a struct holds is what its fields hold, not its type arguments
([#256](https://github.com/boltlang/Bolt/issues/256)): with
`struct Handler[T] { f: fn(T) -> () }`, an `imm Handler[mut [i32]]` is
fine, since a closure doesn't hold what it takes, and with
`struct Frozen[T] { items: imm [T] }`, only an `imm` `T` can be held, in
a `Frozen` of either mutability. That's the same as Rust inferring
`T: 'a` from a struct's fields, and it's what makes a struct type
well-formed (`StructDecl.atMost_ty_iff` in `lean/BoltMut/Structs.lean`).

Unification can't express this, since it's about a type and what's
inside it. It's an "at most" constraint instead, with `imm ⊑ mut`
([#243](https://github.com/boltlang/Bolt/issues/243)): an array or struct
holds only what's at most its own mutability. So `[x]` needs nothing in
the type of `x` to be more `mut` than `imm`. What an array or struct holds
must in turn be at most *its* mutability, and a function's mutability
covers what it captured; what it takes and gives isn't looked into, so an
`imm [fn(mut [i32]) -> ()]` is fine.

The constraint decides what's unknown when only one choice works: a
mutability that must be at most `imm` is `imm`, and one that something
`mut` must be below is `mut`. What's left about a function's parameters
becomes part of an inferred function's type, and its callers must meet it,
like class constraints:

```bolt
fn wrap(x) = Box { item: x };     // forall a. a: imm => fn(a) -> imm Box[a]
wrap(mut [1]);                    // error (E0230): expected a type that's at most `imm`, found `mut [i32]`
```

A signature says it with a bound, `T: imm`, read as "nothing in `T` is
more `mut` than `imm`", like Rust's `T: 'a` for lifetimes. It can be
written next to the parameter or in a `where` clause, and a mutability
can be bounded too, as in `'v: 'm`:

```bolt
fn wrap[T: imm](x: T) -> imm Box[T] = Box { item: x };
fn reader(xs: 'v [i32]) -> 'f fn() -> i32 where 'v: 'f = || xs[0];
impl[T: imm] ToImm[[T]] { ... }          // checked where the impl is chosen
struct Frozen[T: imm] { item: T }        // checked where a value is made
```

Without the bound, a complete signature is an error where it needs one:
in `fn hide[T](x: T) -> i32 { let b = Box { item: x }; 0 }`, `T` may be
`mut`. A `mut` struct can hold anything, so `mut Box { item: x }` needs
nothing. A mutability on its own isn't a type: `let x: imm = 1` is an error
(E0231). A `mut` array or struct inside an `imm` one is still also
caught once the types are known (E0223), which shows the whole type.

**A closure that can change what it captured is `mut`.** A function type
has a mutability like an array's. A closure is `mut` if it captures a
`let mut` variable, even only to read it, or a value that holds something
`mut`: a `mut` array, struct or function. Otherwise it's `imm`, and so is
a named function, which captures nothing. By the rules above, an `imm`
value can't hold a `mut fn`.

Calling a function doesn't need it to be `mut`, unlike Rust's `FnMut`: a
`mut fn` can't be reached from an `imm` value anyway. So a function type
written without `mut` or `imm` in a signature takes either, like `[T]`,
and higher-order functions need no annotations. An `imm fn` is shown as
just `fn`, since most are, unless that would make two types in a message
look the same.

What a closure captures is at most its mutability, by the same "at most"
constraint, and a `let mut` variable makes it `mut`. So a generic function
that makes a closure says how the closure's mutability depends on what it
captured:

```bolt
fn reader(xs: [i32]) = || xs[0];            // 'm: 'n => fn('m [i32]) -> 'n fn() -> i32
fn always[T](x: T) -> fn() -> T = || x;     // forall T. T: 'm => fn(T) -> 'm fn() -> T
fn compose(f, g) = |x| f(g(x));             // forall a b c. 'm: 'o => 'n: 'o => fn('m fn(a) -> b, 'n fn(c) -> a) -> 'o fn(c) -> b
```

In `std`, an `FnIter` whose function counts is `mut`, like the one that
`for x in xs` uses for an array or a `Vec`.

### What this guarantees

**An `imm` value, and everything it holds, never changes.** All the names
for a value have the same type, so if one of them can't change it, none
can, and an `imm` value only holds `imm` ones. A `mut` value can't be seen
as `imm`, which is what makes `imm` worth having:

- code can rely on an `imm` value it's given staying the same;
- values that can't be changed can be shared freely, and their literals can
  be constants: a data segment in Wasm, made once;
- an `imm` struct can't be told apart from a copy, so the code generator
  can store small ones by value;
- the [reactive design](../../reactive.mdx) knows what can change, and which
  calls change it, from the types
  ([#200](https://github.com/boltlang/Bolt/issues/200)).

It doesn't guarantee what Rust does, that nothing else changes a `mut`
value while you have it. `mut` values are shared on purpose.

## Named mutabilities

A name like `'m`, written where `mut` or `imm` would be, is a mutability
that's the same wherever the name is. The
[tutorial](../../../tutorial/advanced/mutability.mdx#naming-a-mutability)
shows how to use them; this section is about how the checker treats them.
`'` marks the name, as for labels and Rust's lifetimes: without it,
`m [i32]` would be the type `m` applied to `i32`.

- **A name is a parameter of the function or impl** whose signature it's
  in, like a hidden one, but shared: every `'m` in the signature, its
  `where` predicates and its body is the same. Names don't need declaring:
  using one is enough. Like a hidden parameter, the caller chooses it, so
  the function can't change what has it, and
  `fn make() -> 'm [i32] = [1]` is an error.
- **Only functions, impls and structs have names.** An impl's associated
  types can use its names too: `impl[T] Iterable['m FnIter[T]] { type Iter =
  'm FnIter[T]; ... }` is for an `FnIter` of either mutability, and its
  `Iter` has the same one. An impl's names, like its type parameters, must
  be in its instance, since that's all choosing the impl decides:
  `impl[T, 'v] Iterable[Vec[T]]` is an error (E0234), and
  `impl[T] Iterable['v Vec[T]]` is what's meant. A name elsewhere, like in
  a const, a type alias outside an impl, a body that isn't its function's
  or a field whose struct doesn't declare it, is an error (E0225). A name
  before a type that can't have a mutability, like `'m i32`, is E0222.
- **Types show names**, and a name for a mutability that's shared but not
  written: one that a body decides, or a variable of an inferred function.
  Such names start at `'m`, so that they don't read like the type variables
  `a`, `b`, ...:

  ```bolt
  fn pick(c, a, b) = if c { array_len(a); a } else { b };  // forall a. fn(Bool, 'm [a], 'm [a]) -> 'm [a]
  fn same(xs: [i32]) -> [i32] = xs;                         // fn('m [i32]) -> 'm [i32]
  fn size(xs) = array_len(xs);                              // forall a. fn([a]) -> i32
  ```

  A mutability that appears once isn't named: it's either, and it isn't
  linked to anything.

### Names in structs

A struct declares its names after its type parameters
([#243](https://github.com/boltlang/Bolt/issues/243)), like
`struct VecIter[T, 'v] { data: 'v Vec[T], index: i32 }`. A type gives
them after its type arguments, like `VecIter[i32, imm]`. One that isn't
given is decided like the mutability before a type: a parameter in a
function's signature, an unknown in a body, and the struct's own in a
field. More than the struct declares is an error (E0232), and so is a
name declared by an item that isn't a struct, a function or an impl
(E0233). A function or an impl can declare its names too, but doesn't
have to.

**A name is at most its struct's mutability.** An `imm VecIter[i32, mut]`
would hold a `mut Vec`, which `imm` being deep rules out. So making a
struct adds `'v ⊑ m` for each name its fields have, where `m` is its
mutability, and what a field with a name holds is at most that name:
`T ⊑ 'v` for `data: 'v Vec[T]`:

```bolt
mut VecIter { data: mut_vec, index: 0 }   // fine: mut VecIter[i32, mut]
VecIter { data: mut_vec, index: 0 }       // error (E0223): an `imm VecIter[i32, mut]` can't have a `mut` mutability argument
fn frozen[T](v: 'v Vec[T]) -> imm VecIter[T, 'v] where 'v: imm = VecIter { data: v, index: 0 };
```

The last one needs `'v: imm`, or `'v` could be `mut`. It doesn't need
`T: imm`: `v` is a `'v Vec[T]`, so `T ⊑ 'v`, which it can assume, since
`v` exists. A struct can bound its names, like its type parameters, which
is checked where a value is made: `struct Frozen['v: imm] { data: 'v [i32] }`.

A struct update, `VecIter { index: 1, ..it }`, keeps the names of `it`,
since the fields it doesn't give are shared. Types show a name that's
known, like `VecIter[i32, imm]`, and leave one out that's generic and
appears once, like the mutability before a type: `VecIter[T]`. One that's
left out before one that's shown is `'_`.

## Open questions

- **A name used once** says nothing that leaving it out doesn't, and could
  be a warning.
- **Impls for struct type constructors.** `impl Functor[Box]` is for boxes
  of either mutability, so `fmap` must return a `Box` with the mutability
  of the one it's given, which it can't make: `Box { item: f(b.item) }` is
  `imm`. Higher-kinded types tie the mutability of the result to that of
  the argument, and what that should mean isn't decided.
  [Regions](./regions.mdx) would let `fmap` make a `Box` of any
  mutability.
- **Enums with a mutability**, so that a variant can hold something that
  can be changed without a type parameter, and so that an enum can be
  changed in place.
- **Assigning to a field of a tuple through a field constraint**, like
  `fn f(t) { t.0 = 1; }`, isn't checked: once the type is a tuple, it's a
  value, and the variable should be `mut`.
