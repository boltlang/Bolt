# Mutability

:::warning[Only in the type checker]
The type checker implements this page. The evaluator still copies arrays
when they're assigned, so programs don't share them yet, and the code
generator doesn't compile arrays at all: see
[#195](https://github.com/boltlang/Bolt/issues/195). The design was decided
in [#196](https://github.com/boltlang/Bolt/issues/196).
:::

Arrays are going to be *shared*: `let ys = xs` makes `ys` another name for
the same array, as in JavaScript, Java and OCaml. Passing an array to a
function then passes a pointer, and a function can fill in an array that
it's given.

Sharing breaks what `mut` on a variable promises:

```bolt
let mut xs = [1, 2];
let ys = xs;     // not `mut`
xs[0] = 9;
ys[0];           // 9: `ys` changed anyway
```

This page describes how the type checker keeps a promise that sharing
can't break. **Whether an array can be changed is part of its type**, and
every name for an array has the same type, so they all agree.

## Arrays have a mutability

The type of an array has a second argument, its *mutability*, which is
`Mut` or `Imm`:

$$
[\tau] \;=\; \mathsf{Array}[\mu, \tau] \qquad \mu ::= \mathsf{Mut} \mid \mathsf{Imm} \mid \alpha
$$

`Mut` and `Imm` are types of a new [kind](./kinds.mdx), $\mathsf{Mutability}$,
so $\mathsf{Array}$ is of kind
$\mathsf{Mutability} \to \mathsf{Type} \to \mathsf{Type}$. A mutability can
be an inference variable, like any type, and it's unified and generalized
like one. That's all the type checker needs: no subtyping and no new kind
of constraint.

In source code, and when types are shown:

| Written | Type | Means |
|---|---|---|
| `mut [i32]` | $\mathsf{Array}[\mathsf{Mut}, \mathsf{i32}]$ | can be changed |
| `imm [i32]` | $\mathsf{Array}[\mathsf{Imm}, \mathsf{i32}]$ | can never be changed, by anyone |
| `[i32]` | $\mathsf{Array}[\alpha, \mathsf{i32}]$ | either: see [annotations](#annotations) |

An array can be changed only if its type is `mut`:

```bolt
fn push[T](xs: mut [T], x: T);    // in `std`

let xs = mut [1, 2];
xs.push(3);      // fine
xs[0] = 9;       // fine

let ys = [1, 2];
ys.push(3);      // error: `ys` is `imm [i32]`, which can't be changed
```

Assigning to an element, `xs[i] = e`, needs `xs` to be a `mut` array. So
does calling a function whose parameter is `mut`, like `push`.

## Where the mutability comes from

**The expression that makes an array decides** whether it can be changed.
Variables only pass it on:

- `[1, 2]` is an array that can't be changed: `imm [i32]`.
- `mut [1, 2]` and `mut []` can be changed: `mut [i32]`.
- A function's result has the mutability of its type: `Vec.new()` could
  return `mut [T]`, and `xs.copy()` a new `mut [T]`.

`let mut` no longer has anything to do with the contents of an array. It
only means the variable can be assigned again:

```bolt
let xs = mut [1];
xs.push(2);         // fine: the array is `mut`
xs = mut [3];       // error: `xs` isn't `mut`

let mut ys = [1];
ys = [2, 3];        // fine: the variable is `mut`
ys.push(4);         // error: the array isn't
```

## Aliases share the mutability

`let ys = xs` unifies the types of `ys` and `xs`, mutability included. So an
alias of a `mut` array is `mut` too, without saying so:

```bolt
let xs = mut [1, 2];
let ys = xs;        // `mut [i32]`, like `xs`
ys.push(3);         // fine, and `xs` sees it
```

Since this is unification, it works however the alias is made: through a
function, a branch, a struct or a closure.

```bolt
fn id(x) = x;

let a = id(xs);                         // `mut [i32]`
let b = if c { xs } else { mut [] };    // `mut [i32]`
let get = || xs;                        // `fn() -> mut [i32]`
```

An alias can't change the mutability. Unifying `Mut` with `Imm` is an error:

```bolt
let xs = mut [1, 2];
let ys: imm [i32] = xs;   // error: expected `imm [i32]`, found `mut [i32]`
```

### What this guarantees

**An `imm` array never changes.** All the names for an array have the same
type, so if one of them can't change it, none can. A `mut` array can't be
seen as `imm`, which is what makes `imm` worth having:

- code can rely on an `imm [i32]` it's given staying the same;
- arrays that can't be changed can be shared freely, and their literals can
  be constants: a data segment in Wasm, made once;
- the [reactive design](../reactive.mdx) knows which arrays can change, and
  which calls change them, from their types
  ([#200](https://github.com/boltlang/Bolt/issues/200)).

It doesn't guarantee what Rust does, that nothing else changes a `mut`
array while you have it. `mut` arrays are shared on purpose.

## Functions

A function without annotations gets the mutability it needs, and is
generalized over the rest, like over any type:

```bolt
fn first(xs) = xs[0];             // fn([a]) -> a
fn fill(xs, x) { xs[0] = x; }     // fn(mut [a], a) -> ()
```

`first` is generalized over the mutability of its argument,
$\forall \mu\, \alpha.\ \mathsf{Array}[\mu, \alpha] \to \alpha$, and that's
shown as `[a]`. It takes arrays of either mutability. `fill` only takes
`mut` ones, since it changes its argument. Instantiating a scheme gives a
fresh mutability, so each call can pass a different kind of array.

## Annotations

**`[T]` in the parameters of a function and in a body means either
mutability**: a fresh mutability, like `_` stands for a fresh type.
`mut [T]` and `imm [T]` ask for one. Where a type stands for one value, like
a return type, `[T]` is `imm`: see [return types](#return-types).

In a function's signature, a fresh mutability is a hidden parameter of the
function, like the generalized $\mu$ of `first` above:

```bolt
fn sum(xs: [i32]) -> i32 { ... }   // forall m. fn(Array[m, i32]) -> i32

let xs = mut [];
xs.push(1);
sum(xs);           // fine
sum([1, 2]);       // fine
```

`sum` takes both kinds of array. Inside its body, the mutability of `xs` is
a parameter, not `Mut`, so `sum` can't change `xs`: `xs.push(1)` there is
an error. That's the same rule as for any type parameter: a function that
takes a `T` can't assume that `T` is `i32`. So a signature promises to
leave an array alone unless it says `mut`, and callers don't have to care
which kind they pass.

It doesn't promise that the array stays the same while `sum` runs: the
caller may have a `mut` name for it. `imm [T]` is for code that relies on
the array never changing, like a cache keyed by it, or the reactive design deciding that something can't
change. Few functions need it, which is why it isn't what `[T]` means.

In a `let` annotation, `[T]` is an inference variable, which the value
decides:

```bolt
let a: [i32] = mut [1];     // `mut [i32]`
let b: [i32] = [1];         // `imm [i32]`
```

### Return types

A hidden parameter is chosen by the caller, so it can't be the mutability
of an array that the function makes: `fn make() -> [i32] = [1, 2]` would be
wrong for a caller that asks for `mut`. So **in a return type, `[T]` is
`imm`**, and `mut [T]` asks for an array that can be changed:

```bolt
fn primes() -> [i32] = [2, 3, 5];            // `fn() -> imm [i32]`
fn buffer() -> mut [u8] = mut [0; 1024];
fn wrong() -> [i32] = mut [];                // error: expected `imm [a]`, found `mut [a]`
```

The same goes for the other places where a type has one value: the type of
a const, a field (see [below](#fields-of-structs)), and an array in a
`where` predicate, like the `[T]` of `where Show[[T]]`, which can't be one
of the hidden parameters of the signature.

An impl gets hidden parameters like a function: `impl Size[[i32]]` is for
arrays of either mutability, and `impl Size[mut [i32]]` only for those
that can be changed.

### Type aliases

A type alias doesn't decide what `[T]` means in it: the type it's used in
does. With `type Ints = [i32]`, `fn sum(xs: Ints)` takes either kind of
array, and `fn make() -> Ints` gives an `imm` one.

### Fields of structs

**A field `[T]` is `imm`**, like a return type, and `mut [T]` asks for an
array that can be changed:

```bolt
struct Inventory {
  name: String,
  items: mut [Item],   // can be changed
  tags: [String],      // can't
}
```

The alternative, "either" as in parameters, would give the struct a hidden
mutability parameter, `Inventory[m]`, so that one `Inventory` can hold a
`mut` array and another an `imm` one. That spreads to every type that
contains an array, much like lifetimes do in Rust.

A field that was meant to be `mut` but isn't written so is found where the
struct is built or its array is changed, rather than where it's declared:
"expected `imm [Item]`, found `mut [Item]`", or "cannot change an element of
`inv.items`, which is `imm [Item]`".

A struct shares its arrays with everything else that refers to them, as
`let` does.

## Making an array that can't be changed from one that can

A `mut` array can't become `imm [T]`, since a `mut` name for it may still
exist. Turning one into the other copies it:

```bolt
fn freeze[T](xs: [T]) -> imm [T];    // a copy that can't be changed
fn thaw[T](xs: [T]) -> mut [T];      // a copy that can
```

Freezing without a copy needs to know that no other name refers to the
array: that it's *unique*. Jane Street's OCaml has a mode for that
[Lorenzen et al. 2024], and it could come later.

## Errors

Changing an element of an array that isn't `mut` is its own error (E0221):

```text
[E0221] Error: cannot change an element of `xs`, which is `imm [i32]`; only a `mut` array can be changed
```

Passing or assigning an array of the wrong mutability is an ordinary type
mismatch, which shows both:

```text
[E0201] Error: expected `mut [i32]`, found `imm [i32]`
```

These can show up far from their cause: the `push` fails because of where
the array was made, maybe much earlier. The error should point at where the
`Imm` came from: the literal, the annotation, or the function whose result
it is. That's what the labels for the causes of constraints in
[#127](https://github.com/boltlang/Bolt/issues/127) are for, and why
unification will have to remember the origin of `Imm` and `Mut`.

## Implementation

- **Types** (`ty.rs`): `Ty::Array` holds the mutability and the element
  type. The mutability is `Ty::Mutability(Mut | Imm)`, an inference
  variable of kind `VarKind::Mutability`, a type parameter, or the error
  type. Mutabilities only ever appear in arrays, and can't be written as
  type arguments, so kind inference doesn't need to know about them.
- **Lowering** (`lower.rs`): `mut [T]` and `imm [T]` lower to their
  mutability, and `[T]` to `Ty::Unwritten`, which each item then replaces
  with `Ty::fill_unwritten`:
  - in a function's parameters and an impl's instance, hidden parameters,
    numbered after the declared type parameters (`FnSig::hidden`,
    `ImplHeader::hidden`), so that instantiating a scheme and matching an
    impl handle them like any other parameter;
  - in a body, inference variables (`infer.rs`);
  - in a return type, a const, a `where` predicate and a field, `Imm`;
  - in a type alias, nothing: the type it's used in decides.
- **Unification** (`unify.rs`): mutabilities are equal or they aren't;
  there's no subtyping.
- **Inference** (`infer.rs`): an array literal is `Imm`, or `Mut` with
  `mut`. Indexing, `for` and slice patterns take either.
  - `check_place` looks for the innermost index of the place that's
    assigned to. With one, the array must be `mut`, and a mutability that
    isn't known yet becomes `Mut`. Without one, the variable must be `mut`,
    as before.
- **Defaulting** (`solve.rs`): a mutability left over when a body is
  checked, and not generalized, becomes `Imm`. That happens after the
  errors are resolved, so that an undecided mutability is shown as `[T]` in
  them.
- **Showing types**: `mut [T]`, `imm [T]`, and `[T]` for a generalized or
  unknown mutability. Schemes leave hidden parameters and generalized
  mutabilities out of their `forall`.
- **Tests**: `tests/checker/array_mutability.txt` has a case for each rule
  on this page.

`Vec[T]` in `std` ([#197](https://github.com/boltlang/Bolt/issues/197))
takes the mutability as a parameter too, `Vec[m, T]`, and `[T]` is
shorthand for it. A `String`
([#199](https://github.com/boltlang/Bolt/issues/199)) could work the same
way, with `mut String` taking the place of a separate `StringBuilder`.

## Open questions

- **Returning what a function is given.** `fn same(xs: [i32]) -> [i32] = xs`
  is an error: `xs` has the hidden parameter's mutability, and the result
  is `imm`. Saying that the result has the mutability of the parameter
  needs a name for it, like a mutability variable. An inferred function,
  `fn same(xs) = xs`, already works.
- **Showing a mutability that's shared.** In
  `fn pick(c, a, b) = if c { a } else { b }`, `a` and `b` have the same
  mutability, and showing both as `[T]` hides that. Types could name the
  mutability only when it's shared, like `fn(Bool, [a]^m, [a]^m) -> [a]^m`,
  with some syntax to write it too.
- **Fields of structs** with a hidden mutability parameter, so that a
  struct can hold arrays of either kind (see [above](#fields-of-structs)).
- **Structs that are shared.** If structs stay values, `p.x = 1` keeps
  needing `let mut p`. If they're shared like arrays, they need a
  mutability too.
- **Other shared types.** Whether `mut` and `imm` before other types, like
  `mut String` or `imm Map[K, V]`, are a general feature for types that have
  a mutability parameter, or only for arrays.

## Prior art

- **OCaml** has no `mut` on variables. Whether a value can change is in its
  type: an `array` always can, a `list` never, and a record field only if
  it's declared `mutable`. Nothing is inferred.
- **Reference immutability**, in Javari [Tschantz & Ernst 2005] and
  ReIm [Huang et al. 2012], puts a read-only qualifier on references in
  Java, and ReIm infers it. There, a read-only reference can point at an
  object that others change. Here, `Imm` means that no one can.
- **Pony's reference capabilities** [Clebsch et al. 2015] decide what each
  reference allows: `iso` (unique), `val` (can't be changed by anyone),
  `ref` (can be changed, and shared), and `box` (read-only, and either of
  the last two). `imm [T]` is like `val`, `mut [T]` like `ref`, and a
  parameter `[T]` like `box`, which Pony gets by subtyping and Bolt by
  polymorphism.
- **Modes in Jane Street's OCaml** [Lorenzen et al. 2024] are qualifiers
  like `unique` and `local`, inferred alongside types. `unique` is what
  freezing without a copy would need.
